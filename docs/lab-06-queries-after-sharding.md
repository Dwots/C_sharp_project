## Часть 1. Архитектура после шардирования

```
                        Backend (GameLib API)
                                │
                         IShardRouter
                     ┌──────────┼──────────┐
                     ▼          ▼          ▼
                  Shard 0    Shard 1    Shard 2
                  :5441      :5442      :5443
```

Router — интерфейс `IShardRouter` с двумя реализациями: `ModuloShardRouter` (`hash(user_id) % 3`) и `ConsistentHashRouter` (кольцо из 300 виртуальных точек). Обе получают на вход shard key и возвращают номер шарда.

Ключ шардирования — **`user_id`**, выбран в работе №5.

Принципиальное ограничение схемы: на шардах лежит **только** `play_sessions`. Справочники `users`, `games`, `categories`, `game_categories` остались в основной базе и на шарды не копировались — это видно в `db/sharding/init-shard.sql`, где создаётся одна таблица и один индекс. Последствия разбираются в части 4.

## Часть 2. Single-Shard Query

### Выбранный запрос

`GET /api/users/{userId}/sessions` — история сессий пользователя, `PlaySessionRepository.GetByUserAsync`:

```sql
SELECT ps.id, ps.user_id, ps.game_id, ps.duration_minutes, ps.platform, ps.created_at
FROM play_sessions ps
WHERE ps.user_id = @UserId
ORDER BY ps.created_at DESC
LIMIT @Limit OFFSET @Offset;
```

Условие `WHERE ps.user_id = @UserId` содержит shard key в виде равенства — это и делает запрос single-shard.

### Проверка: router называет шард

```bash
curl -s -H "X-Api-Key: dev-api-key-12345" \
  "http://localhost:5000/api/sharding/route/42?strategy=modulo"
```

```json
{"userId":42,"strategy":"hash(key) % 3","shardCount":3,"shard":2}
```

### Проверка: данные лежат именно там

```bash
for s in shard0 shard1 shard2; do
  docker compose exec -T $s psql -U gameuser -d shard \
    -c "SELECT count(*) FROM play_sessions WHERE user_id = 42;"
done
```

```
=== shard0 ===      === shard1 ===      === shard2 ===
 rows_user_42        rows_user_42        rows_user_42
--------------      --------------      --------------
            0                   0                  12
```

Вывод подтверждает: все 12 сессий пользователя 42 находятся на shard2, на shard0 и shard1 — ноль строк. Номер шарда, названный router, совпал с тем, где данные реально лежат.

### План запроса на целевом шарде

```bash
docker compose exec -T shard2 psql -U gameuser -d shard -c \
"EXPLAIN ANALYZE SELECT id, game_id, duration_minutes, platform, created_at
 FROM play_sessions WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;"
```

```
 Limit  (cost=38.92..38.94 rows=10 width=30) (actual time=3.285..3.290 rows=12 loops=1)
   ->  Sort  (cost=38.92..38.94 rows=10 width=30) (actual time=3.282..3.284 rows=12 loops=1)
         Sort Key: created_at DESC
         Sort Method: quicksort  Memory: 25kB
         ->  Bitmap Heap Scan on play_sessions  (cost=4.37..38.75 rows=10 width=30) (actual time=0.622..3.217 rows=12 loops=1)
               Recheck Cond: (user_id = 42)
               Heap Blocks: exact=12
               ->  Bitmap Index Scan on idx_shard_user_created  (cost=0.00..4.37 rows=10 width=0) (actual time=0.022..0.023 rows=12 loops=1)
                     Index Cond: (user_id = 42)
 Planning Time: 1.420 ms
 Execution Time: 3.419 ms
```

Что подтверждает вывод: `Index Cond: (user_id = 42)`, `rows=12`, `Execution Time: 3.419 ms` — шард отдаёт результат по индексу за миллисекунды, никаких обращений к соседям в плане нет.

### Почему запросу не нужны другие шарды

Router вычисляет номер шарда **из того же значения**, по которому запись туда попала. При записи `hash(42) % 3` дал 2 — строка ушла на shard2. При чтении та же функция от того же аргумента даёт то же самое 2. Функция детерминированная, значит адрес вычисляется однозначно.

Из этого следует, что строк пользователя 42 на других шардах не может быть **в принципе**: чтобы туда попасть, запись должна была получить другой номер от той же функции с тем же входом. Опрашивать shard0 и shard1 не нужно не потому, что там «скорее всего пусто», а потому, что там гарантированно пусто — вывод `0 / 0 / 12` это и показывает.

Формально: single-shard query — запрос, для которого набор затронутых шардов вычислим до выполнения. Здесь этот набор состоит из одного элемента.

## Часть 3. Агрегирующий запрос

### Выбранный запрос

`GET /api/stats/top-games` — статистика по играм, `PlaySessionRepository.GetTopGamesAsync`:

```sql
SELECT ps.game_id,
       COUNT(*)                   AS sessions_count,
       COUNT(DISTINCT ps.user_id) AS unique_players,
       SUM(ps.duration_minutes)   AS total_minutes,
       ROUND(AVG(ps.duration_minutes), 1) AS avg_minutes
FROM play_sessions ps
WHERE (@From::timestamp IS NULL OR ps.created_at >= @From::timestamp)
GROUP BY ps.game_id
ORDER BY total_minutes DESC
LIMIT @Limit;
```

Здесь присутствуют все четыре вида агрегации из задания: `COUNT`, `SUM`, `AVG`, `GROUP BY`. Shard key (`user_id`) в условиях отсутствует — группировка идёт по `game_id`, а фильтр по `created_at`.

### Проверка: COUNT(*) на каждом шарде

```bash
for s in shard0 shard1 shard2; do
  docker compose exec -T $s psql -U gameuser -d shard -c "SELECT count(*) AS total FROM play_sessions;"
done
```

```
=== shard0 ===      === shard1 ===      === shard2 ===
 total               total               total
-------             -------             -------
 33363               33038               33599
```

Что подтверждает вывод: ни один шард не знает общего числа сессий. Правильный ответ — 33363 + 33038 + 33599 = **100 000** — не хранится нигде и получается только сложением трёх частичных результатов.

### Проверка: топ-3 игры на каждом шарде

```bash
for s in shard0 shard1 shard2; do
  docker compose exec -T $s psql -U gameuser -d shard -c \
  "SELECT game_id, count(*) AS sessions, sum(duration_minutes) AS total_min
   FROM play_sessions GROUP BY game_id ORDER BY total_min DESC LIMIT 3;"
done
```

```
=== shard0 ===                    === shard1 ===                    === shard2 ===
 game_id | sessions | total_min    game_id | sessions | total_min    game_id | sessions | total_min
---------+----------+-----------  ---------+----------+-----------  ---------+----------+-----------
      18 |       45 |      8309        776 |       45 |      8424        363 |       52 |      8715
     469 |       49 |      8197        389 |       51 |      8095        906 |       51 |      8562
     437 |       52 |      8015        364 |       49 |      8064        423 |       54 |      8519
```

Что подтверждает вывод: три списка **не пересекаются ни одной игрой**. У каждого шарда свой «локальный» топ, и лидер одного шарда (`game_id = 363`, 8715 минут) в списки двух других не попал вовсе. При этом ни одно из девяти чисел не является итоговым: сессии игры 363 есть и на shard0, и на shard1, просто там она не вошла в первую тройку.

### Проверка: почему AVG нельзя сложить

```bash
for s in shard0 shard1 shard2; do
  docker compose exec -T $s psql -U gameuser -d shard -c \
  "SELECT count(*) AS cnt, sum(duration_minutes) AS total,
          round(avg(duration_minutes),2) AS avg_min
   FROM play_sessions WHERE game_id = 1;"
done
```

```
=== shard0 ===                  === shard1 ===                  === shard2 ===
 cnt | total | avg_min           cnt | total | avg_min           cnt | total | avg_min
-----+-------+---------         -----+-------+---------         -----+-------+---------
  36 |  5253 |  145.92            37 |  5430 |  146.76            34 |  5639 |  165.85
```

Что подтверждает вывод:

| Способ склейки | Расчёт | Результат |
|---|---|---|
| Среднее от трёх средних | (145.92 + 146.76 + 165.85) / 3 | **152.84** — неверно |
| Сумма / сумма | 16322 / 107 | **152.54** — верно |

Разница 0.30 минуты возникла потому, что у шардов разное число строк (36 / 37 / 34), и среднее по shard2 — самое высокое — было учтено с тем же весом, что и остальные. Отсюда правило: чтобы получить `AVG` по всем шардам, с них нужно забирать не среднее, а **`SUM` и `COUNT` по отдельности**, и делить уже в backend.

### Ответы на вопросы задания

**1. Можно ли выполнить такой запрос только на одном shard?**

Нет. В условиях запроса нет shard key, поэтому вычислить набор нужных шардов заранее невозможно — данные любой игры рассыпаны по всем трём, что и показал вывод по `game_id = 1` (36 / 37 / 34 сессии). Результат с одного шарда не является ни полным, ни даже пропорционально уменьшённым: это частичный ответ по трети пользователей.

Запрос является **distributed**: backend обязан обратиться ко всем шардам и объединить полученное.

**2. Где должны объединяться результаты?**

В backend, на уровне router — единственном месте, которое знает обо всех шардах сразу. PostgreSQL этого сделать не может: три сервера независимы, не знают друг о друге и общего координатора не имеют.

Порядок действий для `top-games`:

1. отправить один и тот же `GROUP BY game_id` на все три шарда **без `LIMIT`** (почему без — разобрано в части 5);
2. получить три набора частичных агрегатов;
3. сложить по `game_id`: `COUNT` и `SUM` суммируются, `AVG` пересчитывается как `SUM/COUNT`;
4. отсортировать объединённый результат и применить `LIMIT`.

Отдельная сложность — `COUNT(DISTINCT ps.user_id)` в исходном запросе. Его нельзя ни сложить, ни пересчитать из частичных чисел: один и тот же пользователь мог бы попасть в счётчики двух шардов, и сумма оказалась бы завышена. В данной схеме спасает выбранный shard key — пользователь целиком лежит на одном шарде, поэтому пересечений между шардами нет и суммирование корректно. При другом ключе (например `created_at`) пришлось бы передавать в backend полные списки идентификаторов.

**3. Что происходит со временем выполнения при увеличении количества shard'ов?**

Работают две противоположные тенденции.

*В пользу шардов:* каждый обрабатывает меньше данных. При росте с 3 до 6 шардов на каждом останется около 16 700 строк вместо 33 000, и локальное сканирование ускорится примерно вдвое. Запросы идут параллельно, поэтому время всей стадии равно времени **самого медленного** шарда, а не сумме.

*Против:* растёт стоимость объединения. Backend делает столько сетевых обращений, сколько шардов, ждёт самого медленного из них и склеивает вдвое больше частичных наборов.

Пока данных много, а шардов немного, выигрывает первое. Дальше кривая выполаживается: ускорять сканирование уже почти нечего, а накладные расходы продолжают расти линейно. В пределе, когда на шарде остаётся по сотне строк, добавление ещё одного только замедляет запрос.

Отдельно стоит отметить худший случай: если один шард отвечает медленно, тормозит **весь** агрегат целиком — результат нельзя отдать, пока не пришла последняя часть. Чем больше шардов, тем выше вероятность, что хотя бы один окажется медленным.

## Часть 4. JOIN между shard'ами

### Выбранный запрос

`GET /api/users/{userId}/sessions` — тот же эндпоинт, что и в части 2, но теперь рассматривается его полная форма с присоединением справочников:

```sql
SELECT ps.id, ps.user_id, u.username, ps.game_id, g.title,
       ps.duration_minutes, ps.platform, ps.created_at
FROM play_sessions ps
JOIN users u ON u.id = ps.user_id
JOIN games g ON g.id = ps.game_id
WHERE ps.user_id = @UserId
ORDER BY ps.created_at DESC
LIMIT @Limit OFFSET @Offset;
```

Сессия сама по себе хранит только числовые идентификаторы. Имя пользователя и название игры берутся из `users` и `games` — без этих двух JOIN эндпоинт вернул бы `user_id: 42, game_id: 252` вместо читаемых значений.

### Где находятся связанные данные

```bash
docker compose exec -T shard2 psql -U gameuser -d shard -c "\dt"
docker compose exec -T postgres psql -U gameuser -d gamelibdb -c "\dt"
```

```
=== SHARD2 ===
 Schema |     Name      | Type  |  Owner
--------+---------------+-------+----------
 public | play_sessions | table | gameuser
(1 row)

=== ОСНОВНАЯ БАЗА ===
 public | categories            | table
 public | game_categories       | table
 public | games                 | table
 public | play_sessions         | partitioned table
 public | play_sessions_2024_09 | table
 ...                                                  (45 relations)
 public | user_games            | table
 public | users                 | table
```

Что подтверждает вывод: на шарде **одна-единственная таблица** — `play_sessions`. Справочники `users`, `games`, `categories`, `game_categories` находятся только в основной базе. Стороны JOIN лежат на разных серверах:

```
Shard 2 (:5443)            Основная база (:5434)
play_sessions          users / games
      │                          │
      └────────── JOIN ──────────┘
                  ?
```

### Проверка: JOIN на шарде выполнить нельзя

```bash
docker compose exec -T shard2 psql -U gameuser -d shard -c \
"SELECT ps.id, u.username, g.title, ps.duration_minutes
 FROM play_sessions ps
 JOIN users u ON u.id = ps.user_id
 JOIN games g ON g.id = ps.game_id
 WHERE ps.user_id = 42 LIMIT 5;"
```

```

LINE 3:  JOIN users u ON u.id = ps.user_id
```

Тот же запрос в основной базе, где обе стороны рядом:

```

---------+----------+-----------+------------------
 1077065 | user_41  | Game #252 |              243
 1139037 | user_41  | Game #453 |               28

```

Что подтверждает сравнение: запрос синтаксически корректен и прекрасно работает — ломает его не SQL, а физическое расположение таблиц. Планировщик PostgreSQL видит только содержимое своего экземпляра; для shard2 таблицы `users` не существует, и до выполнения дело не доходит вовсе, ошибка возникает на этапе разбора запроса.

### Ответы на вопросы задания

**1. Что произойдёт, если связанные записи находятся на разных shard'ах?**

Запрос не выполнится. Полученная ошибка `relation "users" does not exist` — это и есть ответ в чистом виде: каждый PostgreSQL знает только собственные таблицы и о существовании соседей не подозревает.

Соединять данные придётся вне базы:

1. шард отдаёт сессии с голыми `user_id` и `game_id`;
2. backend собирает встретившиеся идентификаторы;
3. backend отдельным запросом тянет `username` и `title` из основной базы;
4. backend сшивает два набора в памяти.

Иначе говоря, JOIN не исчезает — он **переезжает из базы в код приложения**. Вместе с ним переезжают и все обязанности планировщика: выбор порядка соединения, выбор алгоритма (hash join / nested loop), использование индексов. В приложении всё это превращается в ручной цикл по словарю.

**2. Можно ли выполнить такой JOIN обычным SQL-запросом к одному PostgreSQL?**

Нет. Обычный запрос ограничен одним экземпляром, и любая таблица вне его для запроса не существует.

Технически обойти это можно расширениями `postgres_fdw` или `dblink`: они подключают внешнюю таблицу как локальную, и JOIN снова становится записываемым на SQL. Но это уже не «обычный запрос»: требуется установка расширения, описание внешнего сервера и таблиц, а исполнение всё равно означает передачу данных по сети между серверами — со всеми задержками и без гарантий транзакционности. В данной работе такой путь не применялся.

**3. Какие данные пришлось бы передавать между shard'ами?**

Есть два направления, и они сильно различаются по стоимости.

| Вариант | Что передаётся | Объём |
|---|---|---|
| Тянуть справочники к сессиям | `users` + `games` целиком на каждый шард | ~3 МБ на шард, разово |
| Тянуть сессии к справочникам | все строки `play_sessions` со всех шардов в одно место | сотни МБ на каждый запрос |

Разница принципиальна: справочники маленькие и почти не меняются, сессии огромные и растут постоянно. Поэтому передавать нужно **справочники**, а не данные.

Стандартное название приёма — **reference tables** (справочные таблицы): небольшие редко изменяемые таблицы копируются целиком на каждый шард. После этого `JOIN users` и `JOIN games` выполняются внутри шарда обычным SQL, и исходный запрос сервиса снова работает как есть, без переписывания.

Плата — дублирование: одна и та же строка `users` хранится в трёх экземплярах, и при изменении её нужно обновлять на всех шардах. Для справочника на 10 000 строк, где изменения редки, это приемлемая цена; для `play_sessions` такой подход был бы бессмысленным — он свёл бы шардирование на нет.

**4. Можно ли выбрать shard key так, чтобы этот JOIN чаще выполнялся внутри одного shard?**

Для двух JOIN ответ разный.

*`JOIN users` — да.* У `users` есть естественный ключ той же природы, что и shard key: `users.id` — это и есть `user_id`. Если шардировать `users` по тому же правилу `hash(id) % 3`, то пользователь и все его сессии попадут на один шард: обе стороны соединяются по значению, из которого вычисляется адрес, значит и адрес у них совпадёт. Этот приём называется **co-location** — размещение связанных таблиц по общему ключу. JOIN становится локальным без всякого дублирования.

*`JOIN games` — нет.* `games` связана с сессиями по `game_id`, а шард определяется по `user_id`. Эти значения независимы: сессии одной игры принадлежат разным пользователям и разъезжаются по всем шардам, что уже было видно в части 3 (`game_id = 1` нашлась на всех трёх, 36 / 37 / 34 строки). Co-location невозможна в принципе: нельзя разместить одну строку `games` так, чтобы она оказалась рядом со всеми своими сессиями сразу. Единственное решение для `games` — репликация справочника, вариант из вопроса 3.

Общий вывод: shard key выравнивает ровно одну связь — ту, что идёт по нему самому. Все прочие связи либо решаются репликацией маленьких таблиц, либо остаются распределёнными.

## Часть 5. ORDER BY + LIMIT

### Выбранный запрос

`GET /api/stats/top-games` заканчивается сортировкой с ограничением:

```sql
GROUP BY ps.game_id
ORDER BY total_minutes DESC
LIMIT @Limit;
```

Второй запрос сервиса с `ORDER BY ... ### Почему недостаточно первых 100 записей с одного shard

Каждый шард хранит примерно треть пользователей и, соответственно, треть сессий. Его рейтинг построен по этой трети и о двух других ничего не знает. Результат такого рейтинга — ответ на вопрос «какие игры популярны среди трети пользователей», а не «какие игры популярны».

Формально: `ORDER BY` задаёт порядок на **всём** множестве строк, а `LIMIT` отсекает от него начало. Шард же располагает лишь подмножеством и сортирует только его. Строка, стоящая в подмножестве на первом месте, в полном множестве может оказаться на любом — что и показали игры 776 и 363.

Правильный порядок действий:

1. запросить у **всех** шардов их частичные данные;
2. объединить в backend;
3. отсортировать объединённый набор;
4. применить `LIMIT`.

`LIMIT` обязан быть последним. Применённый до объединения, он отбросит строки, которые после суммирования оказались бы в начале — случай игры 351.

### Отдельно: сколько строк забирать с каждого шарда

Здесь есть тонкость, разделяющая два случая.

**Сортировка по значению самой строки** (например `ORDER BY created_at DESC LIMIT 100`). Достаточно взять по 100 строк с каждого шарда и слить 300 в одну сортировку. Это корректно: чтобы строка попала в глобальную сотню, она обязана быть в сотне лучших на своём шарде — если на её же шарде есть 100 строк новее, то и во всём наборе их не меньше 100. Передаётся `N × количество шардов` строк вместо всей таблицы.

**Сортировка по агрегату** — наш случай, `ORDER BY sum(duration_minutes)`. Такой приём уже неверен: итоговое значение складывается из трёх частей, и каждая часть по отдельности может быть скромной. Игра 351 — ровно этот случай: три средних результата дали второе место в мире. Поэтому `GROUP BY` приходится забирать с шардов **целиком**, без `LIMIT`, и ограничивать уже после суммирования. Объём передаваемых данных здесь определяется не `LIMIT`, а числом групп — в данном случае 1000 игр × 3 шарда.

### Ответы на вопросы задания

**1. Какие данные становятся недоступны?**

33 599 сессий — треть всех записей. Это не случайная треть, а данные пользователей, для которых `hash(user_id) % 3 = 2`. Каждый такой пользователь теряется **целиком**: и история, и статистика, и возможность записать новую сессию. Обратная сторона локальности — тот самый эффект, который делает запросы быстрыми, при отказе делает потерю полной.

Справочники `users`, `games`, `categories` не затронуты: они в основной базе.

**2. Какие endpoint'ы перестанут работать?**

| Эндпоинт | Состояние при отказе shard2 |
|---|---|
| `GET /api/users/{id}/sessions` | не работает для пользователей shard2, работает для остальных двух третей |
| `GET /api/users/{id}/activity` | то же |
| `POST /api/users/{id}/sessions` | запись для пользователей shard2 невозможна |
| `GET /api/stats/top-games` | работает, но результат неполный — посчитан по двум третям данных |
| `GET /api/sharding/distribution` | **500**, подтверждено выводом |
| `GET /api/sharding/route/{id}` | работает, подтверждено выводом |

Запросы делятся ровно по признаку из части 2: single-shard страдают только те, чей ключ указывает на упавший шард; distributed страдают все.

Отдельного внимания заслуживает `top-games`. Технически он способен вернуть ответ по двум живым шардам — и это хуже явной ошибки: пользователь получит `200 OK` и правдоподобные цифры, не подозревая, что треть данных не учтена.

**3. Продолжит ли работать остальная часть сервиса?**

Да — при условии, что backend написан соответствующим образом. Проверка 2 показала: shard0 отдаёт данные без задержек и не знает об отказе соседа. Шарды независимы, общей точки отказа между ними нет.

Но текущая реализация этим не пользуется: проверка 4 показала `500` на `distribution`, где ответ пропал полностью, хотя две трети информации были собраны. `ShardingService.GetDistributionAsync` обходит шарды последовательным циклом, первое же исключение прерывает метод. Это честная демонстрация типичной ошибки — потенциальная отказоустойчивость архитектуры не реализуется сама собой, её нужно закладывать в код.

**4. Что должен делать backend при обращении к недоступному shard?**

- **Ограничить время ожидания.** Без `Timeout` в строке подключения запрос к мёртвому шарду зависает до сетевого таймаута ОС, и вместе с ним зависает поток обработки.
- **Не ронять весь ответ.** Для distributed-запросов правильное поведение — вернуть частичный результат с явной пометкой «shard2 недоступен, данные неполные», а не `500`. Решение о том, годятся ли неполные данные, принимает вызывающая сторона, и обмануть её молчаливым `200 OK` недопустимо.
- **Отвечать быстро и по существу.** Для single-shard-запроса к упавшему шарду уместен `503 Service Unavailable` с `Retry-After` — он означает «сервис жив, эти данные временно недоступны», в отличие от `500`, который сообщает о поломке сервиса вообще.
- **Не долбиться в мёртвый сервер.** Circuit breaker: после нескольких неудач шард помечается недоступным, и запросы к нему сразу отклоняются, не тратя таймаут. Периодическая проверка возвращает его в строй.
- **Различать чтение и запись.** Запись в упавший шард можно поставить в очередь и применить после восстановления; чтение отложить нельзя — данные нужны сейчас.

**5. Как можно повысить отказоустойчивость?**

Основной способ — **реплика у каждого шарда**, то есть соединение механизмов из работ №4 и №5:

```
      Shard 0            Shard 1            Shard 2
    Primary ──► Replica  Primary ──► Replica  Primary ──► Replica
```

Шардирование делит данные и защищает от нехватки объёма; репликация дублирует данные и защищает от потери узла. Это разные задачи, и одно другое не заменяет: шарды не хранят копий друг друга, поэтому сами по себе отказоустойчивости не дают — что и показала проверка 1. В промышленных конфигурациях их всегда применяют вместе.

Дополнительно:

- **автоматический failover** — при падении Primary реплика повышается до Primary, router переключается на неё; вручную это минуты простоя, автоматически — секунды;
- **health check шардов** в backend — фоновая проверка доступности, чтобы не узнавать об отказе от первого пострадавшего пользователя;
- **алерты** — механизм из работы №3 (`TelegramAlertService`) применим здесь без изменений: недоступность шарда — такое же событие, как отсутствие партиции;
- **резервные копии каждого шарда** — защита от потери тома, которую репликация не покрывает (ошибочный `DELETE` доедет до реплики за миллисекунды).

## Часть 7. Hot Shard

### Проверка: профиль шардов

```bash
for s in shard0 shard1 shard2; do
  docker compose exec -T $s psql -U gameuser -d shard -c \
  "SELECT count(*) AS users, sum(c) AS rows, round(avg(c),2) AS avg_per_user, max(c) AS max_per_user
   FROM (SELECT user_id, count(*) AS c FROM play_sessions GROUP BY user_id) t;"
done
```

| Шард | Пользователей | Строк | Сессий на пользователя (среднее) | Максимум у одного |
|---|---|---|---|---|
| shard0 | 3342 | 33363 | 9.98 | 22 |
| shard1 | 3315 | 33038 | 9.97 | 23 |
| shard2 | 3344 | 33599 | 10.05 | 25 |

```bash
for s in shard0 shard1 shard2; do
  docker compose exec -T $s psql -U gameuser -d shard -c \
  "SELECT user_id, count(*) AS sessions FROM play_sessions GROUP BY user_id ORDER BY sessions DESC LIMIT 5;"
done
```

```
=== shard0 ===            === shard1 ===            === shard2 ===
 user_id | sessions        user_id | sessions        user_id | sessions
---------+----------      ---------+----------      ---------+----------
    6445 |       22           6250 |       23           5090 |       25
    2995 |       21           3874 |       22           7520 |       24

    1917 |       20           1118 |       22           3043 |       23
    2551 |       20           6884 |       21           1963 |       22
```

Что подтверждает вывод: распределение практически идеальное. Пользователей на шардах 3342 / 3315 / 3344, строк 33363 / 33038 / 33599, среднее число сессий на пользователя 9.98 / 9.97 / 10.05. Самый активный пользователь во всём наборе имеет 25 сессий при среднем 10 — превышение в 2.5 раза, чего недостаточно, чтобы перекосить шард из 33 тысяч строк.

**Hot shard на этих данных не воспроизводится**, и причина в том, откуда данные взялись: они созданы генератором `db/seed/generate_data.sql`, который выбирает пользователя для каждой сессии равномерно случайно. В реальном сервисе такого распределения не бывает, поэтому дальнейший разбор ведётся как анализ рисков, а не как описание наблюдаемого состояния.

### Возможные причины перекоса 10% / 15% / 75%

**Неудачный shard key.** Ключ с малым числом различных значений (`platform` — 3-4 значения, `game_id` — 1000) физически не способен распределить данные ровно. Крайний случай — `platform`: шард с «PC» получил бы большинство сессий просто потому, что таких сессий больше.

**Неравномерное распределение данных.** Хеш-функция распределяет ровно **ключи**, но не объём данных за ними. В части 3 работы №5 это уже наблюдалось: Consistent Hashing с FNV-1a дал 42.20% / 20.61% / 37.19% строк при равном числе виртуальных узлов — точки легли на кольцо неравномерно. Строки при этом никто не перекашивал специально.

**Популярный пользователь или tenant.** Главный риск ключа `user_id`. Один пользователь всегда целиком на одном шарде — это достоинство ключа, ставшее его слабостью. Появление аккаунта с миллионом сессий (стример, бот, корпоративный клиент) делает его шард горячим, и **никакая перебалансировка не помогает**: разделить одного пользователя между шардами выбранный ключ не позволяет. В измеренных данных максимум 25 сессий; в реальном сервисе распределение активности подчиняется закону Ципфа, где несколько процентов пользователей дают большую часть трафика.

**Определённый тип запросов.** Нагрузку создают не строки, а обращения. Аналитический запрос, перебирающий историю одного пользователя целиком, стоит дороже тысячи точечных чтений, и если такие запросы адресованы пользователям одного шарда, нагрузка сместится туда при полностью равном числе строк.

### Почему равное количество строк ещё не означает равномерную нагрузку

Потому что это две разные величины, и измеряются они в разных единицах: строки — это **хранение**, нагрузка — это **обращения в секунду**. Связь между ними отсутствует.

На измеренных данных: shard0 и shard2 отличаются по числу строк на 0.7%. Но если из 3344 пользователей shard2 активны сегодня 800, а из 3342 пользователей shard0 — 200, shard2 обслужит вчетверо больше запросов при том же объёме хранения. Распределение строк этого не показывает и показать не может: `count(*)` считает то, что лежит, а не то, к чему обращаются.

Конкретные механизмы расхождения:

| Причина | Пример |
|---|---|
| Разная активность пользователей | 90% пользователей неактивны, их строки лежат мёртвым грузом |
| Разная стоимость запроса | один `GROUP BY` по истории пользователя ≫ тысяча чтений по `id` |
| Соотношение чтений и записей | шард с активными игроками принимает `INSERT`, остальные только читают |
| Неравномерность во времени | вечерний пик по часовым поясам смещает нагрузку на шарды с пользователями из этого региона |

Практический вывод: балансировку нельзя проверять по `count(*)`. Нужны метрики обращений — запросов в секунду на шард, времени ответа, загрузки CPU. Настроенные в проекте Prometheus и Grafana дают именно эти величины; распределение строк из части 4 работы №5 отвечает лишь на вопрос «где что лежит».

### Плюсы — какие запросы стали эффективными

| Эндпоинт | Почему эффективен | Подтверждение |

| `GET /api/users/{id}/sessions` | `WHERE user_id = ?` — router вычисляет единственный шард | часть 2: 0 / 0 / 12 строк, `Execution Time: 3.419 ms` |
| `GET /api/users/{id}/activity` | то же условие, агрегат считается внутри одного шарда | — |
| `POST /api/users/{id}/sessions` | адрес записи известен до обращения, запись идёт в один шард без распределённой транзакции | — |

Это три из четырёх основных операций сервиса, и они же самые частые: история и запись сессий выполняются на каждое действие пользователя, аналитика — изредка.

Дополнительное следствие, менее очевидное: `COUNT(DISTINCT user_id)` в `top-games` суммируется по шардам корректно. Пользователь целиком принадлежит одному шарду, поэтому в счётчики двух шардов попасть не может, и пересечений нет (часть 3). При другом ключе этот агрегат потребовал бы передачи полных списков идентификаторов.

### Минусы — какие запросы стали распределёнными

| Операция | Что произошло |
|---|---|
| `GET /api/stats/top-games` | `GROUP BY game_id` идёт поперёк ключа: опрос всех шардов, суммирование в backend, `AVG` пересчёт через `SUM`/`COUNT` (часть 3) |
| `JOIN games` | `game_id` не связан с `user_id`, co-location невозможна (часть 4) |
| Любой отчёт по периоду или платформе | `created_at` и `platform` в ключ не входят — опрос всех шардов |
| Сортировка по агрегату | `LIMIT` применим только после склейки, с шардов забираются все группы (часть 5) |

### Проблемные операции

| Операция | Сложность | Причина |
|---|---|---|
| **JOIN** | высокая | `users` решается co-location, `games` — только репликацией справочника; подтверждено ошибкой `relation "users" does not exist` |
| **Aggregation** | высокая | опрос всех шардов, ручная склейка, `AVG` и `COUNT(DISTINCT)` требуют отдельной логики |
| **ORDER BY + LIMIT** | высокая для агрегатов | игра 351 — вторая в глобальном топе и ни в одном локальном топ-5 |
| **Migration** | высокая | изменение схемы применяется к трём базам; Liquibase в проекте настроен на одну |
| **Backup** | средняя | три независимых дампа; согласованного среза на общий момент времени не существует |
| **Восстановление** | высокая | шарды восстановятся на разные моменты; частичная доступность (часть 6: `500` вместо ответа по двум живым шардам) |
| **Балансировка** | средняя | смягчается Consistent Hashing: 18.35% переезда против 75.2% у `hash % N` (работа №5); но тяжёлого пользователя разделить нельзя в принципе |

Самые тяжёлые — те, что идут поперёк ключа (aggregation, JOIN по `game_id`) и те, что затрагивают все шарды сразу (migration, восстановление).

### Вывод: оставить ключ или выбрать другой

**Ключ `user_id` оставить.**

Обоснование — соотношение частот. Шардируют не ради красоты схемы, а ради конкретной нагрузки, и в GameLib API она устроена так: обращения к истории и запись сессий происходят постоянно, аналитика по играм — эпизодически. `user_id` делает частые операции однокадресными ценой удорожания редких. Обратный выбор (`game_id`) ускорил бы `top-games` и превратил бы каждый запрос истории в опрос всех шардов — размен явно невыгодный.

Альтернативы, рассмотренные в работе №5, слабее по измеримым признакам:

- `created_at` — сессии одного пользователя разъезжаются по шардам, главный запрос сервиса становится распределённым;
- `id` сессии — распределение идеальное, но локальности нет вообще;
- `game_id` — 1000 различных значений, популярные игры создают перекос, а запрос истории всё равно распределённый.

При проектировании заново изменились бы не ключ, а сопутствующие решения:

1. **Справочники сразу как reference tables.** `users` и `games` вместе занимают 3 МБ (часть 4) — их следовало копировать на каждый шард с самого начала, тогда исходный SQL сервиса работал бы на шарде без переписывания.
2. **Реплика у каждого шарда.** Схема из работы №4, применённая к каждому шарду: проверка 1 части 6 показала, что отказ одного узла уносит треть пользователей целиком.
3. **Отдельное хранилище для аналитики.** `top-games` плохо ложится на шардированные данные при любом ключе. Промышленное решение — считать статистику заранее и хранить в отдельной таблице, а не собирать по трём базам на каждый запрос.
4. **Обработка недоступного шарда в коде.** Частичный ответ с пометкой вместо `500` — текущая реализация теряет собранные данные при отказе одного узла.

Смена ключа ни одну из этих проблем не решает — все они относятся к архитектуре вокруг ключа, а не к нему самому. Это и есть главный итог работы: правильно выбранный shard key убирает часть трудностей, но остальные переносит в код приложения, где их приходится решать явно.

## Вопросы для самопроверки

**1. Чем single-shard query отличается от distributed query?**

Набором шардов, который можно вычислить до выполнения. У single-shard он состоит из одного элемента, потому что shard key присутствует в условии: `WHERE user_id = 42` → `hash(42) % 3 = 2` → shard2. У distributed ключа в условии нет, и приходится опрашивать все шарды с последующей склейкой в backend. Первый обслуживается одним сервером за миллисекунды (3.419 ms в части 2), второй стоит N сетевых обращений и требует логики объединения.

**2. Почему JOIN между shard'ами сложнее обычного JOIN?**

Потому что обычный JOIN выполняет планировщик одной базы: он видит обе таблицы, их статистику и индексы, выбирает алгоритм и порядок соединения. При разнесении таблиц по серверам этого не остаётся — PostgreSQL знает только свои таблицы, и запрос падает на разборе: `relation "users" does not exist` (часть 4). Соединение переезжает в приложение вместе со всеми обязанностями планировщика, причём вручную и без статистики.

**3. Как выполнить COUNT(*) по всем shard'ам?**

Отправить `SELECT count(*)` на каждый шард и сложить полученное в backend: 33363 + 33038 + 33599 = 100 000 (часть 3). Ни один шард общего числа не знает. С `SUM` так же; с `AVG` нельзя — среднее от средних даёт 152.84 против верных 152.54, забирать нужно `SUM` и `COUNT` по отдельности и делить после склейки.

**4. Почему ORDER BY ... LIMIT требует объединения результатов?**

Потому что `ORDER BY` задаёт порядок на всём множестве строк, а шард сортирует только свою треть. Позиция строки в подмножестве ничего не говорит о её позиции в полном множестве: лидер shard1 (игра 776) в глобальную пятёрку не вошёл, а глобальный лидер (игра 389) не был первым нигде (часть 5). `LIMIT` поэтому применяется последним — после сбора и сортировки объединённого набора.

**5. Что произойдёт при отказе одного shard?**

Его данные становятся недоступны целиком — 33 599 сессий, треть пользователей (часть 6). Остальные шарды продолжают работать: shard0 отдал данные пользователя 470 при выключенном shard2. Single-shard-запросы к живым шардам не страдают, distributed-запросы либо падают (`500` на `distribution`), либо возвращают неполный результат. Router продолжает отвечать, поскольку выполняет арифметику, а не обращение к базе.

**6. Что такое hot shard?**

Шард, принимающий непропорционально большую долю нагрузки. Причины: неудачный ключ с малым числом значений, неравномерное попадание хешей, один очень активный пользователь, перекос по типам запросов. Ключевое свойство — hot shard возможен при идеально равном числе строк, потому что строки измеряют хранение, а нагрузка измеряется обращениями (часть 7).

**7. Почему выбор shard key влияет на JOIN?**

JOIN локален, когда обе стороны лежат на одном сервере, а это определяется ключом. `JOIN users ON u.id = ps.user_id` можно сделать локальным, шардировав `users` по тому же `user_id`: соединение идёт по значению, из которого вычисляется адрес, значит адреса совпадут (co-location). `JOIN games ON g.id = ps.game_id` локальным не сделать: `game_id` и `user_id` независимы, сессии одной игры принадлежат разным пользователям и разъезжаются по всем шардам (часть 3: `game_id = 1` найдена на всех трёх). Ключ выравнивает ровно одну связь — ту, что идёт по нему самому.

**8. Какие операции особенно плохо подходят для распределённых данных?**

JOIN между таблицами с разными ключами; агрегаты, не сводящиеся к сложению (`AVG`, `COUNT(DISTINCT)`, медиана); сортировка по агрегату с `LIMIT`; транзакции, затрагивающие несколько шардов (в `DistributeAsync` отката между шардами нет); `UNIQUE` и внешние ключи через границу шарда — база не может их проверить; согласованный backup на общий момент времени.

**9. Что произойдёт при изменении количества shard'ов?**

Часть ключей меняет адрес и требует физического переноса. Масштаб зависит от стратегии: при `hash % N` с 3 на 4 шарда переехали 75.2% записей, при Consistent Hashing — 18.35% (работа №5). Причина разницы в том, что позиции точек на кольце не зависят от числа шардов, поэтому новый шард отрезает куски у существующих, не сдвигая остальные. Во время переноса система либо недоступна, либо работает по двум схемам одновременно.

**10. Чем шардирование отличается от репликации?**

Репликация хранит **одни и те же** данные на нескольких серверах, шардирование — **разные части** данных. Отсюда разные задачи: репликация масштабирует чтение и защищает от потери узла, шардирование масштабирует объём и запись. Отказ реплики не теряет данных, отказ шарда делает треть данных недоступной (часть 6). Механизмы не взаимозаменяемы и в промышленных системах применяются вместе: каждому шарду — своя реплика.

**11. Может ли шардирование сделать отдельный SQL-запрос быстрее?**

Да, но не за счёт распараллеливания, а за счёт уменьшения объёма. На шарде лежит треть данных — таблица и индексы меньше, дерево индекса ниже, страниц читается меньше. В части 2 запрос по `user_id = 42` выполнился за 3.419 ms при `Heap Blocks: exact=12`.

Для distributed-запросов ответ сложнее: параллельная работа шардов помогает, но время определяется самым медленным из них плюс склейка в backend. Отдельный запрос, которому нужны все шарды, после шардирования чаще становится медленнее, а не быстрее.
