# Лабораторная работа №6 — Запросы и архитектура после шардирования

## Часть 1. Архитектура после шардирования

```
                        Backend (GameLib API)
                                │
                         IShardRouter
                     ┌──────────┼──────────┐
                     ▼          ▼          ▼
                  Shard 0    Shard 1    Shard 2
                  :5441      :5442      :5443
```

Shard key — `user_id`, выбран в работе №5. Router (`IShardRouter`) считает `hash(user_id) % 3` и возвращает номер шарда.

На шардах лежит только `play_sessions`. Справочники `users`, `games`, `categories` остались в основной базе — это понадобится в части 4.

## Часть 2. Single-Shard Query

Запрос — история сессий пользователя, `GET /api/users/{userId}/sessions`:

```sql
SELECT ps.id, ps.game_id, ps.duration_minutes, ps.platform, ps.created_at
FROM play_sessions ps
WHERE ps.user_id = @UserId
ORDER BY ps.created_at DESC
LIMIT @Limit OFFSET @Offset;
```

**Спрашиваем у router, куда он отправит пользователя 42:**

```bash
curl -s -H "X-Api-Key: dev-api-key-12345" \
  "http://localhost:5000/api/sharding/route/42?strategy=modulo"
```

```json
{"userId":42,"strategy":"hash(key) % 3","shardCount":3,"shard":2}
```

**Проверяем все три шарда — где реально лежат его сессии:**

```bash
for s in shard0 shard1 shard2; do
  docker compose exec -T $s psql -U gameuser -d shard \
    -c "SELECT count(*) FROM play_sessions WHERE user_id = 42;"
done
```

```
=== shard0 ===      === shard1 ===      === shard2 ===
            0                   0                  12
```

**Смотрим план запроса на целевом шарде:**

```bash
docker compose exec -T shard2 psql -U gameuser -d shard -c \
"EXPLAIN ANALYZE SELECT id, game_id, duration_minutes, platform, created_at
 FROM play_sessions WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;"
```

```
 Limit  (cost=38.92..38.94 rows=10 width=30) (actual time=3.285..3.290 rows=12 loops=1)
   ->  Sort  (cost=38.92..38.94 rows=10 width=30) (actual time=3.282..3.284 rows=12 loops=1)
         Sort Key: created_at DESC
         ->  Bitmap Heap Scan on play_sessions  (actual time=0.622..3.217 rows=12 loops=1)
               Recheck Cond: (user_id = 42)
               Heap Blocks: exact=12
               ->  Bitmap Index Scan on idx_shard_user_created  (actual time=0.022..0.023 rows=12 loops=1)
                     Index Cond: (user_id = 42)
 Execution Time: 3.419 ms
```

### Почему запросу не нужно обращаться к другим shard'ам

Router вычисляет номер шарда из того же значения, по которому запись туда попала: при вставке `hash(42) % 3` дал 2, при чтении та же функция от того же аргумента даёт то же 2. Функция детерминированная, поэтому строк пользователя 42 на других шардах быть не может — что и показал вывод `0 / 0 / 12`.

## Часть 3. Агрегирующий запрос

Запрос — статистика по играм, `GET /api/stats/top-games`:

```sql
SELECT ps.game_id, COUNT(*), COUNT(DISTINCT ps.user_id),
       SUM(ps.duration_minutes), ROUND(AVG(ps.duration_minutes), 1)
FROM play_sessions ps
GROUP BY ps.game_id
ORDER BY SUM(ps.duration_minutes) DESC
LIMIT @Limit;
```

Shard key в условиях нет — группировка идёт по `game_id`.

**Считаем строки на каждом шарде:**

```bash
for s in shard0 shard1 shard2; do
  docker compose exec -T $s psql -U gameuser -d shard -c "SELECT count(*) FROM play_sessions;"
done
```

```
=== shard0 ===      === shard1 ===      === shard2 ===
        33363               33038               33599
```

33363 + 33038 + 33599 = 100 000. Общего числа не знает ни один шард.

**Берём одну игру и смотрим её агрегаты на каждом шарде:**

```bash
for s in shard0 shard1 shard2; do
  docker compose exec -T $s psql -U gameuser -d shard -c \
  "SELECT count(*) AS cnt, sum(duration_minutes) AS total,
          round(avg(duration_minutes),2) AS avg_min
   FROM play_sessions WHERE game_id = 1;"
done
```

```
=== shard0 ===                  === shard1 ===                  === shard2 ===
 cnt | total | avg_min           cnt | total | avg_min           cnt | total | avg_min
  36 |  5253 |  145.92            37 |  5430 |  146.76            34 |  5639 |  165.85
```

| Способ склейки AVG | Расчёт | Результат |
|---|---|---|
| Среднее от трёх средних | (145.92 + 146.76 + 165.85) / 3 | 152.84 — неверно |
| Сумма / сумма | 16322 / 107 | 152.54 — верно |

### Ответы на вопросы

**1. Можно ли выполнить такой запрос только на одном shard?**

Нет. Сессии одной игры принадлежат разным пользователям и лежат на всех шардах — `game_id = 1` нашлась на всех трёх (36 / 37 / 34). Результат с одного шарда — ответ по трети пользователей.

**2. Где должны объединяться результаты?**

В backend: три PostgreSQL независимы и друг о друге не знают. `COUNT` и `SUM` складываются, `AVG` пересчитывается как сумма делённая на сумму — из вывода видно, что среднее от средних даёт 152.84 вместо 152.54, потому что число строк на шардах разное.

**3. Что происходит со временем выполнения при увеличении количества shard'ов?**

Речь идёт о распределённых запросах — single-shard от числа шардов только выигрывают, им по-прежнему нужен один сервер, и данных на нём становится меньше.

Для распределённых работают две противоположные тенденции. Каждый шард обрабатывает меньше данных и сканирует быстрее — но сканирование ограничено снизу нулём, а накладные расходы растут линейно: чем больше шардов, тем больше сетевых обращений и тем больше частичных наборов надо сложить. Пока данных на шарде много, выигрывает ускорение сканирования; когда его уже почти нечего ускорять, добавление шарда только замедляет.

Опрос идёт параллельно, поэтому общее время равно не сумме, а времени самого медленного шарда. Отдать ответ раньше нельзя — сумма неполна, пока не пришла последняя часть. Чем больше шардов, тем выше вероятность, что хотя бы у одного сейчас плохая миллисекунда, и он задержит весь запрос.

## Часть 4. JOIN между shard'ами

Полная форма запроса из части 2 — с присоединением справочников:

```sql
FROM play_sessions ps
JOIN users u ON u.id = ps.user_id
JOIN games g ON g.id = ps.game_id
```

**Смотрим, какие таблицы есть на шарде и какие в основной базе:**

```bash
docker compose exec -T shard2 psql -U gameuser -d shard -c "\dt"
docker compose exec -T postgres psql -U gameuser -d gamelibdb -c "\dt"
```

```
=== SHARD2 ===                    === ОСНОВНАЯ БАЗА ===
 public | play_sessions | table    public | categories      | table
(1 row)                            public | games           | table
                                   public | play_sessions   | partitioned table
                                   public | users           | table
                                   ...                      (45 relations)
```

**Пробуем выполнить JOIN прямо на шарде:**

```bash
docker compose exec -T shard2 psql -U gameuser -d shard -c \
"SELECT ps.id, u.username, g.title FROM play_sessions ps
 JOIN users u ON u.id = ps.user_id
 JOIN games g ON g.id = ps.game_id
 WHERE ps.user_id = 42 LIMIT 5;"
```

```
ERROR:  relation "users" does not exist
LINE 3:  JOIN users u ON u.id = ps.user_id
```

**Тот же запрос в основной базе, где обе таблицы рядом:**

```
   id    | username |   title   | duration_minutes
 1077065 | user_41  | Game #252 |              243
 1139037 | user_41  | Game #453 |               28
 1299926 | user_41  | Game #52  |              129
```

**Смотрим размер справочников — понадобится для ответа 3:**

```bash
docker compose exec -T postgres psql -U gameuser -d gamelibdb -c \
"SELECT 'users', count(*), pg_size_pretty(pg_total_relation_size('users')) FROM users
 UNION ALL SELECT 'games', count(*), pg_size_pretty(pg_total_relation_size('games')) FROM games;"
```

```
   t   | count |  size
 users | 10001 | 2904 kB
 games |  1001 | 256 kB
```

### Ответы на вопросы

**1. Что произойдёт, если связанные записи находятся на разных shard'ах?**

Запрос не выполнится: `relation "users" does not exist`. Соединять придётся в backend — забрать сессии с шарда, отдельно вытащить `username` и `title` из основной базы и сшить в памяти. JOIN не исчезает, а переезжает из базы в код.

**2. Можно ли выполнить такой JOIN обычным SQL-запросом к одному PostgreSQL?**

Нет, запрос ограничен одним экземпляром. Обойти можно расширениями `postgres_fdw` или `dblink`, но это уже не обычный запрос и данные всё равно идут по сети.

**3. Какие данные пришлось бы передавать между shard'ами?**

Справочники целиком — `users` и `games` вместе занимают 3 МБ, тогда как `play_sessions` в работе №5 весила 727 МБ. Приём называется reference tables: маленькие редко меняющиеся таблицы копируются на каждый шард, и JOIN снова выполняется локально. Обратный вариант — тащить сессии в одно место — означал бы сотни мегабайт на каждый запрос.

**4. Можно ли выбрать shard key так, чтобы этот JOIN чаще выполнялся внутри одного shard?**

Для `users` — да: если шардировать её по тому же `user_id`, пользователь и его сессии попадут на один шард (co-location). Для `games` — нет: `game_id` и `user_id` независимы, сессии одной игры разъезжаются по всем шардам, и разместить строку `games` рядом со всеми её сессиями невозможно. Остаётся только репликация справочника.

### Почему недостаточно получить первые 100 записей только с одного shard

Шард сортирует только свою треть данных, поэтому его рейтинг отвечает на вопрос «что популярно среди трети пользователей». Позиция в подмножестве не совпадает с позицией в полном наборе: лидер shard1 (игра 776) в глобальную пятёрку не попал вовсе, а глобальный лидер 389 не был первым нигде.

Игра 351 показывает, что мало и по 5 записей с каждого шарда: она набрала второе место суммой трёх средних результатов, ни один из которых не дотянул до местной пятёрки. Поэтому `LIMIT` применяется последним — после сбора со всех шардов и сортировки объединённого набора.

## Часть 6. Отказ одного shard

**Гасим shard2 и проверяем, что он действительно недоступен:**

```bash
docker compose stop shard2
docker compose exec -T shard2 psql -U gameuser -d shard \
  -c "SELECT count(*) FROM play_sessions WHERE user_id = 42;"
```

```
gamelib_shard0       Up 11 minutes (healthy)
gamelib_shard1       Up 11 minutes (healthy)

service "shard2" is not running
```

Пользователь 42, найденный в части 2, теперь недоступен полностью.

**Обращаемся к живому шарду — проверяем, что он не пострадал:**

```bash
docker compose exec -T shard0 psql -U gameuser -d shard \
  -c "SELECT count(*) FROM play_sessions WHERE user_id = 470;"
```

```
 count
    13
```

**Дёргаем router — он к базам не обращается:**

```bash
curl -s -i ... "http://localhost:5000/api/sharding/route/42?strategy=modulo"
```

```
HTTP/1.1 200 OK
{"userId":42,"strategy":"hash(key) % 3","shardCount":3,"shard":2}
```

**Дёргаем эндпоинт, которому нужны все шарды:**

```bash
curl -s ... "http://localhost:5000/api/sharding/distribution"
docker compose logs --tail=40 api | grep -iE "npgsql|exception"
```

```
distribution -> 500
gamelib_api | at Npgsql.NpgsqlCommand.ExecuteScalar(Boolean async, CancellationToken cancellationToken)
gamelib_api | at GameLibApi.Middleware.ExceptionHandlingMiddleware.InvokeAsync(HttpContext context)
```

**Возвращаем шард:**

```bash
docker compose start shard2
```

```json
[{"shard":0,"rows":33363},{"shard":1,"rows":33038},{"shard":2,"rows":33599}]
```

Данные вернулись сами — шард хранит их на своём томе.

### Ответы на вопросы

**1. Какие данные становятся недоступны?**

33 599 сессий — треть всех записей, принадлежащих пользователям с `hash(user_id) % 3 = 2`. Каждый такой пользователь теряется целиком: и история, и статистика, и возможность записать новую сессию. Справочники не затронуты, они в основной базе.

**2. Какие endpoint'ы перестанут работать?**

| Эндпоинт | Состояние |
|---|---|
| `GET /api/users/{id}/sessions` | не работает для пользователей shard2, для остальных двух третей работает |
| `GET /api/users/{id}/activity` | то же |
| `POST /api/users/{id}/sessions` | запись для пользователей shard2 невозможна |
| `GET /api/stats/top-games` | отвечает, но результат посчитан по двум третям данных |
| `GET /api/sharding/distribution` | 500 |
| `GET /api/sharding/route/{id}` | работает |

**3. Продолжит ли работать остальная часть сервиса?**

Да — shard0 отдал данные пользователя 470 при выключенном shard2. Но текущий код этим не пользуется: `distribution` вернул 500, хотя две трети информации уже были собраны — цикл по шардам прерывается на первом исключении.

**4. Что должен делать backend при обращении к недоступному shard?**

Ограничивать время ожидания, иначе поток зависает до сетевого таймаута. Для распределённых запросов — возвращать частичный результат с пометкой о недоступном шарде вместо 500. Для запроса к конкретному упавшему шарду — `503` с `Retry-After`, а не `500`. Плюс circuit breaker, чтобы не тратить таймаут на заведомо мёртвый сервер.

**5. Как можно повысить отказоустойчивость?**

Дать каждому шарду реплику — соединить механизмы работ №4 и №5:

```
      Shard 0            Shard 1            Shard 2
    Primary ─► Replica  Primary ─► Replica  Primary ─► Replica
```

Шардирование делит данные, репликация их дублирует; шарды копий друг друга не хранят, поэтому сами по себе от отказа не защищают. Дополнительно — автоматический failover, health check шардов в backend и алерты (механизм `TelegramAlertService` из работы №3 применим без изменений).

## Часть 7. Hot Shard

**Смотрим профиль каждого шарда — сколько пользователей и насколько они активны:**

```bash
for s in shard0 shard1 shard2; do
  docker compose exec -T $s psql -U gameuser -d shard -c \
  "SELECT count(*) AS users, sum(c) AS rows, round(avg(c),2) AS avg_per_user, max(c) AS max_per_user
   FROM (SELECT user_id, count(*) AS c FROM play_sessions GROUP BY user_id) t;"
done
```

| Шард | Пользователей | Строк | Сессий на пользователя | Максимум у одного |
|---|---|---|---|---|
| shard0 | 3342 | 33363 | 9.98 | 22 |
| shard1 | 3315 | 33038 | 9.97 | 23 |
| shard2 | 3344 | 33599 | 10.05 | 25 |

Распределение практически идеальное, hot shard на этих данных не воспроизводится: генератор `db/seed/generate_data.sql` выбирает пользователя равномерно случайно, поэтому самый активный имеет 25 сессий при среднем 10. Дальше — разбор рисков, а не наблюдаемого состояния.

### Возможные причины перекоса

- **Неудачный shard key** — ключ с малым числом значений (`platform` — 3-4 значения) физически не способен распределить данные ровно.
- **Неравномерное распределение данных** — хеш распределяет ровно ключи, но не объём за ними. В работе №5 Consistent Hashing на FNV-1a дал 42.20% / 20.61% / 37.19% при равном числе виртуальных узлов.
- **Популярный пользователь** — главный риск ключа `user_id`. Пользователь всегда целиком на одном шарде, и аккаунт с миллионом сессий делает свой шард горячим. Перебалансировка не помогает: разделить одного пользователя выбранный ключ не позволяет.
- **Определённый тип запросов** — аналитика по истории одного пользователя стоит дороже тысячи точечных чтений.

### Почему равное количество строк ещё не означает равномерную нагрузку

Строки измеряют хранение, нагрузка измеряется обращениями в секунду — это разные величины. Если из 3344 пользователей shard2 сегодня активны 800, а из 3342 пользователей shard0 — 200, shard2 обслужит вчетверо больше запросов при том же объёме данных. `count(*)` считает то, что лежит, а не то, к чему обращаются.

Отсюда практический вывод: балансировку проверяют по метрикам обращений — запросов в секунду, времени ответа, загрузке CPU (Prometheus и Grafana в проекте), а не по распределению строк.

## Часть 8. Итоговый анализ shard key

Ключ — `user_id`.

### Плюсы

| Эндпоинт | Почему эффективен |
|---|---|
| `GET /api/users/{id}/sessions` | `WHERE user_id = ?` — один шард, 3.419 ms (часть 2) |
| `GET /api/users/{id}/activity` | то же условие, агрегат считается внутри шарда |
| `POST /api/users/{id}/sessions` | адрес записи известен заранее, распределённой транзакции нет |

Это три из четырёх основных операций сервиса и самые частые. Дополнительно `COUNT(DISTINCT user_id)` в `top-games` суммируется корректно: пользователь целиком на одном шарде, пересечений между шардами нет.

### Минусы

| Операция | Что произошло |
|---|---|
| `GET /api/stats/top-games` | `GROUP BY game_id` идёт поперёк ключа — опрос всех шардов и склейка в backend |
| `JOIN games` | `game_id` не связан с `user_id`, co-location невозможна |
| Отчёты по периоду или платформе | эти поля в ключ не входят |

### Проблемные операции

| Операция | Сложность | Причина |
|---|---|---|
| JOIN | высокая | `users` решается co-location, `games` — только репликацией справочника |
| Aggregation | высокая | опрос всех шардов, `AVG` и `COUNT(DISTINCT)` требуют отдельной логики |
| ORDER BY | высокая для агрегатов | `LIMIT` применим только после склейки (игра 351) |
| Migration | высокая | схема применяется к трём базам, Liquibase настроен на одну |
| Backup | средняя | три независимых дампа, согласованного среза не существует |
| Восстановление | высокая | шарды восстановятся на разные моменты |
| Балансировка | средняя | Consistent Hashing даёт 18.35% переезда против 75.2%, но тяжёлого пользователя разделить нельзя |

### Вывод

**Ключ оставить.** Обращения к истории и запись сессий происходят постоянно, аналитика по играм — эпизодически, и `user_id` делает частые операции однокадресными ценой удорожания редких. Обратный выбор (`game_id`) ускорил бы `top-games` и превратил бы каждый запрос истории в опрос всех шардов.

При проектировании заново изменился бы не ключ, а решения вокруг него: справочники сразу как reference tables, реплика у каждого шарда, отдельное хранилище для предпосчитанной аналитики и обработка недоступного шарда в коде вместо 500. Смена ключа ни одну из этих проблем не решает.

## Вопросы для самопроверки

**1. Чем single-shard query отличается от distributed query?**
Набором шардов, вычислимым заранее. У single-shard в условии есть shard key, поэтому адрес один. У distributed ключа нет — опрашиваются все шарды и результат склеивается в backend.

**2. Почему JOIN между shard'ами сложнее обычного JOIN?**
Планировщик видит только таблицы своей базы, поэтому запрос падает на разборе: `relation "users" does not exist`. Соединение приходится делать в приложении вручную, без статистики и выбора алгоритма.

**3. Как выполнить COUNT(*) по всем shard'ам?**
Отправить `count(*)` на каждый шард и сложить: 33363 + 33038 + 33599 = 100 000. С `AVG` так нельзя — нужно забирать `SUM` и `COUNT` отдельно.

**4. Почему ORDER BY ... LIMIT требует объединения результатов?**
Шард сортирует только свою треть, и позиция в ней не совпадает с глобальной: лидер shard1 в мировую пятёрку не вошёл.

**5. Что произойдёт при отказе одного shard?**
Треть данных станет недоступна целиком. Остальные шарды продолжат работать, distributed-запросы либо упадут, либо вернут неполный результат.

**6. Что такое hot shard?**
Шард, принимающий непропорционально большую долю нагрузки. Возможен при идеально равном числе строк, потому что строки — это хранение, а нагрузка — обращения.

**7. Почему выбор shard key влияет на JOIN?**
JOIN локален, когда обе стороны на одном сервере, а это определяет ключ. `users` можно разместить рядом с сессиями по общему `user_id`, `games` — нельзя, `game_id` от `user_id` не зависит.

**8. Какие операции особенно плохо подходят для распределённых данных?**
JOIN между таблицами с разными ключами, агрегаты вроде `AVG` и `COUNT(DISTINCT)`, сортировка по агрегату с `LIMIT`, транзакции через несколько шардов, `UNIQUE` и внешние ключи через границу шарда, согласованный backup.

**9. Что произойдёт при изменении количества shard'ов?**
Часть ключей сменит адрес и потребует переноса: при `hash % N` с 3 на 4 шарда переехали 75.2% записей, при Consistent Hashing — 18.35% (работа №5).

**10. Чем шардирование отличается от репликации?**
Репликация хранит одни и те же данные на нескольких серверах и защищает от потери узла, шардирование хранит разные части и масштабирует объём. Механизмы не взаимозаменяемы и применяются вместе.

**11. Может ли шардирование сделать отдельный SQL-запрос быстрее?**
Да, за счёт меньшего объёма данных на шарде: запрос из части 2 выполнился за 3.419 ms. Distributed-запрос чаще становится медленнее — его время определяется самым медленным шардом плюс склейка.
