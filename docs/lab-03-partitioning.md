# Лабораторная работа №3 — Партиционирование PostgreSQL

> Партиционирование — не просто `PARTITION BY RANGE (...)`. В production-системе
> нужно думать обо всём жизненном цикле: спроектировать → создать → заполнить →
> использовать → создавать новые → контролировать → обнаруживать сбои → восстанавливать.

## Часть 1. RANGE PARTITIONING по дате

```sql
CREATE TABLE events (
    id         BIGINT      NOT NULL,
    user_id    BIGINT      NOT NULL,
    event_type VARCHAR(50) NOT NULL,
    payload    TEXT,
    created_at TIMESTAMP   NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_09_09 PARTITION OF events FOR VALUES FROM ('2026-09-09') TO ('2026-09-10');
CREATE TABLE events_2026_09_10 PARTITION OF events FOR VALUES FROM ('2026-09-10') TO ('2026-09-11');
CREATE TABLE events_2026_09_11 PARTITION OF events FOR VALUES FROM ('2026-09-11') TO ('2026-09-12');
```

Загружено 300 000 строк, равномерно распределённых по трём суткам.

```sql
SELECT tableoid::regclass AS partition_name, COUNT(*)
FROM events GROUP BY tableoid ORDER BY partition_name;
```

```
  partition_name   | count
-------------------+--------
 events_2026_09_09 | 100288
 events_2026_09_10 |  99944
 events_2026_09_11 |  99768
```

Каждая строка физически лежит ровно в одной партиции. Псевдоколонка `tableoid` показывает, в какой именно — для самого приложения таблица при этом выглядит как одна.

### Ответы

**1. В какую партицию попадёт запись с `created_at = '2026-09-10 12:00:00'`?**

В `events_2026_09_10`. Проверено вставкой:

```
   id   |     created_at      |     партиция
--------+---------------------+-------------------
 900001 | 2026-09-10 12:00:00 | events_2026_09_10
```

**2. В какую партицию попадёт запись с `created_at = '2026-09-11 00:00:00'`?**

В `events_2026_09_11` — уже в следующую:

```
 900002 | 2026-09-11 00:00:00 | events_2026_09_11
```

Хотя партиция `events_2026_09_10` объявлена как `TO ('2026-09-11')`, эта полночь в неё не попадает.

**3. Что произойдёт, если вставить запись за 2026-09-12?**

Вставка завершится ошибкой — подходящей партиции не существует:

```
ERROR:  no partition of relation "events" found for row
DETAIL:  Partition key of the failing row contains (created_at) = (2026-09-12 10:00:00).
```

Это ключевой факт для всей работы: **отсутствие партиции — не деградация производительности, а полный отказ записи**. Приложение начнёт падать на `INSERT`. Именно поэтому части 10 и 11 посвящены автоматическому созданию партиций и контролю их наличия.

**4. Почему граница `TO ('2026-09-11')` не включает эту дату?**

Границы диапазона в PostgreSQL полуоткрытые: `FROM` включается, `TO` исключается — математически это `[FROM, TO)`.

Сделано так не из прихоти, а чтобы соседние партиции стыковались без зазоров и без пересечений. Если бы обе границы включались, значение `2026-09-11 00:00:00` подходило бы сразу под две партиции, и СУБД не смогла бы решить, куда его класть. При полуоткрытых границах `TO` одной партиции совпадает с `FROM` следующей, и любое значение попадает ровно в одну.

## Часть 2. Partition pruning

### Запрос по ключу партиционирования

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM events
WHERE created_at >= '2026-09-10' AND created_at < '2026-09-11';
```

```
 Aggregate  (cost=2608.99..2609.00 rows=1 width=8) (actual time=24.884..24.886 rows=1 loops=1)
   Buffers: shared hit=860
   ->  Seq Scan on events_2026_09_10 events  (actual time=0.009..17.370 rows=99945 loops=1)
         Filter: ((created_at >= '2026-09-10'::timestamp) AND (created_at < '2026-09-11'::timestamp))
         Buffers: shared hit=860
 Execution Time: 24.931 ms
```

| Вопрос                               | Ответ                                                                    |
| ------------------------------------ | ------------------------------------------------------------------------ |
| Сколько партиций проверил PostgreSQL | **одну**                                                                 |
| Какая партиция действительно нужна   | `events_2026_09_10`                                                      |
| Удалось ли исключить остальные       | да, обе                                                                  |
| Где в плане видно pruning            | по **отсутствию** узлов: в плане нет `Append` и нет двух других партиций |

Главное наблюдение: partition pruning не отображается отдельной строкой плана. Он проявляется тем, что ненужные партиции **вообще не появляются** в дереве. Вместо ожидаемого `Append` из трёх узлов план состоит из единственного `Seq Scan` по нужной партиции.

### Запрос не по ключу партиционирования

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM events WHERE event_type = 'click';
```

```
 Finalize Aggregate  (actual time=26.586..31.585 rows=1 loops=1)
   Buffers: shared hit=2582
   ->  Gather  (Workers Launched: 2)
         ->  Partial Aggregate
               ->  Parallel Append  (actual time=0.014..20.028 rows=25068 loops=3)
                     Buffers: shared hit=2582
                     ->  Parallel Seq Scan on events_2026_09_09 events_1
                           Filter: ((event_type)::text = 'click'::text)
                           Rows Removed by Filter: 25013
                     ->  Parallel Seq Scan on events_2026_09_10 events_2
                     ->  Parallel Seq Scan on events_2026_09_11 events_3
 Execution Time: 31.585 ms
```

### Сравнение

| Метрика              | По `created_at` (ключ) | По `event_type` (не ключ) |
| -------------------- | ---------------------- | ------------------------- |
| Партиций просмотрено | **1 из 3**             | **3 из 3**                |
| Узел плана           | `Seq Scan`             | `Parallel Append`         |
| Buffers              | **860**                | **2582**                  |
| Execution Time       | 24.9 ms                | 31.6 ms                   |

Отношение буферов 2582 / 860 = ровно 3 — то есть во втором случае прочитана вся таблица целиком, по всем партициям.

### Почему второй запрос обращается ко всем партициям

Потому что PostgreSQL распределяет строки по партициям **только по ключу партиционирования**. Про `event_type` схема разбиения ничего не знает: события с `event_type = 'click'` есть в каждом дне, а значит и в каждой партиции.

Исключить партицию планировщик может лишь тогда, когда способен **доказать** по условию запроса, что подходящих строк там нет. Условие по `created_at` такое доказательство даёт: границы партиций заданы именно по этой колонке. Условие по `event_type` — нет, поэтому приходится смотреть везде.

Отсюда практическое правило: **partition pruning работает только для условий по ключу партиционирования.** Если запрос фильтрует по другой колонке, партиционирование ему не помогает — нужен индекс.

## Часть 3. RANGE PARTITIONING по числовому значению

Партиционирование не обязано быть по дате — подходит любая колонка с естественным порядком.

```sql
CREATE TABLE products (id BIGINT NOT NULL, name TEXT NOT NULL, price NUMERIC NOT NULL)
  PARTITION BY RANGE (price);

CREATE TABLE products_cheap     PARTITION OF products FOR VALUES FROM (0)    TO (100);
CREATE TABLE products_medium    PARTITION OF products FOR VALUES FROM (100)  TO (1000);
CREATE TABLE products_expensive PARTITION OF products FOR VALUES FROM (1000) TO (MAXVALUE);
```

Добавлено 8 товаров с ценами от 15 до 95 000:

```
      партиция      | count |   min   |   max
--------------------+-------+---------+----------
 products_cheap     |     3 |   15.00 |    99.99
 products_medium    |     3 |  100.00 |   890.00
 products_expensive |     2 | 1500.00 | 95000.00
```

Границы подтвердились наглядно: товар за `99.99` попал в `cheap`, а ровно `100.00` — уже в `medium`. Та же полуоткрытость `[FROM, TO)`, что и с датами.

`MAXVALUE` в верхней границе означает «без ограничения сверху» — иначе товар дороже фиксированного потолка вызвал бы ту же ошибку `no partition found`.

### Какие партиции PostgreSQL должен просмотреть и почему

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM products WHERE price >= 100 AND price < 500;
```

```
 Seq Scan on products_medium products  (actual time=0.006..0.008 rows=2 loops=1)
   Filter: ((price >= '100'::numeric) AND (price < '500'::numeric))
   Rows Removed by Filter: 1
   Buffers: shared hit=1
 Execution Time: 0.023 ms
```

**Только `products_medium`** — и это вытекает из арифметики границ:

| Партиция             | Диапазон      | Пересекается с `[100, 500)`?                   |
| -------------------- | ------------- | ---------------------------------------------- |
| `products_cheap`     | `[0, 100)`    | нет — заканчивается там, где запрос начинается |
| `products_medium`    | `[100, 1000)` | **да**                                         |
| `products_expensive` | `[1000, ∞)`   | нет — начинается выше верхней границы запроса  |

Планировщик сравнивает границы запроса с границами партиций и отбрасывает те, что заведомо не пересекаются. Обратите внимание, что `products_cheap` исключена именно благодаря полуоткрытости: `[0, 100)` и `[100, 500)` не имеют ни одной общей точки.

## Часть 4. LIST PARTITIONING

Когда данные делятся не по диапазону, а по категориям.

```sql
CREATE TABLE customers (id BIGINT NOT NULL, name TEXT NOT NULL, customer_type VARCHAR(30) NOT NULL)
  PARTITION BY LIST (customer_type);

CREATE TABLE customers_b2c        PARTITION OF customers FOR VALUES IN ('B2C');
CREATE TABLE customers_b2b        PARTITION OF customers FOR VALUES IN ('B2B');
CREATE TABLE customers_enterprise PARTITION OF customers FOR VALUES IN ('Enterprise');
```

Загружено 30 000 клиентов:

```
       партиция       | count
----------------------+-------
 customers_b2c        |  9917
 customers_b2b        |  9984
 customers_enterprise | 10099
```

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM customers WHERE customer_type = 'B2B';
```

```
 Seq Scan on customers_b2b customers  (actual time=0.019..2.228 rows=9984 loops=1)
   Filter: ((customer_type)::text = 'B2B'::text)
   Buffers: shared hit=71
```

### Ответы

**Какая партиция используется?**
Только `customers_b2b`. Остальные три, включая `DEFAULT`, в план не попали.

**Почему PostgreSQL может не обращаться к другим?**
Потому что при `LIST` каждое значение ключа **явно приписано** к конкретной партиции. Значение `'B2B'` перечислено в `FOR VALUES IN ('B2B')`, поэтому планировщик знает наверняка: в `customers_b2c` и `customers_enterprise` таких строк не может быть в принципе — СУБД сама не позволила бы их туда положить.

Отдельно стоит отметить, что и `customers_default` исключена. Раз `'B2B'` явно закреплено за своей партицией, в DEFAULT оно попасть не могло.

**Чем такой сценарий отличается от RANGE?**

|                             | RANGE                                            | LIST                                  |
| --------------------------- | ------------------------------------------------ | ------------------------------------- |
| Как задаётся принадлежность | границами интервала `[FROM, TO)`                 | явным перечислением значений          |
| Как планировщик исключает   | сравнивает границы запроса и партиции            | проверяет вхождение значения в список |
| Работает с запросами        | `=`, `<`, `>`, `BETWEEN`                         | практически только `=` и `IN`         |
| Новое значение ключа        | попадает в существующий диапазон, если он покрыт | требует новой партиции или DEFAULT    |
| Типичное применение         | время, цена, числовые диапазоны                  | статус, тип, регион, страна           |

Главное различие практическое: диапазон для RANGE можно задать с запасом, и новые значения будут в него попадать сами. Для LIST каждое новое значение категории нужно заводить явно — что и приводит к следующей части.

## Часть 5. LIST PARTITIONING: неизвестное значение

```sql
INSERT INTO customers VALUES (100, 'Test User', 'VIP');
```

```
ERROR:  no partition of relation "customers" found for row
DETAIL:  Partition key of the failing row contains (customer_type) = (VIP).
```

Тип `VIP` не перечислен ни в одной партиции — вставка отклонена.

```sql
CREATE TABLE customers_default PARTITION OF customers DEFAULT;
```

После создания DEFAULT та же вставка проходит:

```
       партиция       | count
----------------------+-------
 customers_b2c        |  9917
 customers_b2b        |  9984
 customers_enterprise | 10099
 customers_default    |     1
```

### Ответы

**1. Зачем нужна DEFAULT partition?**

Это «партиция-приёмник» для всех значений ключа, не подошедших ни к одной из объявленных. Без неё любое незапланированное значение приводит к отказу записи, а не к деградации — приложение падает на `INSERT`.

**2. Чем она полезна?**

Прежде всего тем, что превращает **фатальную ошибку в терпимое неудобство**. Появился новый тип клиента, которого не предусмотрели при проектировании, — данные сохранятся, сервис продолжит работать, а разработчики заведут нормальную партицию позже, без аварии в ночи.

Это же делает её страховкой при эволюции схемы: список категорий в живой системе меняется, и DEFAULT даёт запас времени между появлением нового значения и реакцией на него.

**3. Какие проблемы возникают, если постоянно складывать новые значения в DEFAULT?**

Четыре, и все накапливаются незаметно.

**Она растёт без ограничений и теряет смысл разбиения.** Если основной поток данных оседает в DEFAULT, партиционирования фактически нет — есть одна большая таблица и несколько маленьких рядом.

**Pruning по ней почти не работает.** Планировщик не знает, какие значения лежат в DEFAULT — там может оказаться что угодно. Поэтому в запрос по значению, не закреплённому явно, DEFAULT попадёт обязательно, даже если нужных строк в ней нет.

**Она блокирует создание новых партиций.** Чтобы завести партицию под значение, уже попавшее в DEFAULT, PostgreSQL обязан просканировать её целиком и убедиться, что переносимых строк не осталось. На большой DEFAULT это долгая операция с блокировкой.

**Проблема маскируется.** Ошибка `no partition found` заметна сразу; молчаливое накопление в DEFAULT не проявляется никак, пока кто-нибудь не посмотрит на её размер.

Практический вывод: DEFAULT нужна как страховка, но попадание в неё должно отслеживаться — непустая DEFAULT это сигнал «заведите партицию», а не штатный режим.

## Часть 6. HASH PARTITIONING

```sql
CREATE TABLE user_events (
    id BIGINT NOT NULL, user_id BIGINT NOT NULL,
    event_type VARCHAR(50), created_at TIMESTAMP NOT NULL
) PARTITION BY HASH (user_id);

CREATE TABLE user_events_0 PARTITION OF user_events FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE user_events_1 PARTITION OF user_events FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE user_events_2 PARTITION OF user_events FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE user_events_3 PARTITION OF user_events FOR VALUES WITH (MODULUS 4, REMAINDER 3);
```

Загружено 400 000 строк со случайными `user_id`:

```
   партиция    | count  | процент
---------------+--------+---------
 user_events_0 | 100549 |   25.14
 user_events_1 | 100079 |   25.02
 user_events_2 |  99732 |   24.93
 user_events_3 |  99640 |   24.91
```

### Ответы

**1. Насколько равномерно распределились данные?**

Практически идеально: разброс от 24.91% до 25.14% при теоретических 25%. Отклонение меньше четверти процента.

Равномерность здесь не случайность, а прямое следствие свойств хеш-функции: она «перемешивает» значения так, что остаток от деления распределяется равномерно независимо от того, как распределены сами `user_id`.

**2. Почему HASH может быть полезен?**

Главное применение — **равномерность объёма**. При RANGE по дате партиции получаются разного размера: в чёрную пятницу событий в разы больше, чем в обычный вторник. HASH даёт партиции одинакового размера по построению.

Из этого следуют практические выгоды: предсказуемое время обслуживающих операций (`VACUUM`, перестроение индекса) на каждой партиции; отсутствие «горячей» партиции, в которую бьёт вся текущая нагрузка на запись — при RANGE по дате все вставки идут в сегодняшнюю партицию, при HASH они размазаны; и естественная основа для будущего шардирования, где партиции разъезжаются по разным серверам.

**3. Чем HASH отличается от RANGE?**

|                                 | RANGE                      | HASH                        |
| ------------------------------- | -------------------------- | --------------------------- |
| Принадлежность                  | по значению ключа          | по остатку от хеша          |
| Порядок сохраняется             | **да**                     | **нет**                     |
| Размеры партиций                | неравномерные              | равные                      |
| Pruning для `=`                 | работает                   | работает                    |
| Pruning для диапазона `BETWEEN` | **работает**               | **не работает**             |
| Добавить партицию               | просто, следующий интервал | требует пересчёта `MODULUS` |
| Удалить старые данные           | `DROP` партиции            | невозможно                  |

Ключевое различие в одной строке: **HASH уничтожает порядок**. Соседние по времени события расходятся по разным партициям, поэтому диапазонный запрос обязан просмотреть все.

**4. Почему HASH плохо подходит для сценария «удалить данные старше 3 лет»?**

Потому что при HASH записи трёхлетней давности **равномерно размазаны по всем партициям** — по построению, ведь распределение идёт по `user_id`, а не по времени. Нет ни одной партиции, которую можно было бы целиком признать устаревшей.

В результате удаление превращается в обычный `DELETE ... WHERE created_at < ...` по всем партициям: долгая операция, генерирующая мусор, который потом убирает `VACUUM`, с раздуванием таблиц и журнала.

При RANGE по дате та же задача решается командой `DROP TABLE events_2023_01` — мгновенно, без чтения данных, без мусора, без нагрузки на журнал. Именно эта возможность чаще всего и оказывается главной причиной выбрать партиционирование по времени.

## Часть 7. Выбор стратегии партиционирования

| Сценарий                                                                          | Стратегия                   | Обоснование                                                                                                                                                                                                                                                                          |
| --------------------------------------------------------------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A.** Миллионы событий в день, через 3 года удалять данные старше 3 лет          | **RANGE по дате**           | Только RANGE по времени позволяет удалить устаревшие данные через `DROP TABLE` партиции — мгновенно и без нагрузки. При любой другой стратегии старые записи размазаны по всем партициям и удаляются построчным `DELETE`.                                                            |
| **B.** Три типа пользователей (B2C / B2B / Enterprise), запросы фильтруют по типу | **LIST по `customer_type`** | Значений мало, они дискретны и известны заранее, а основной фильтр запросов идёт ровно по этой колонке — pruning оставит одну партицию. Для трёх категорий RANGE был бы искусственной натяжкой.                                                                                      |
| **C.** Равномерно распределить данные по разделам по `user_id`                    | **HASH по `user_id`**       | Задача сформулирована именно как равномерность, а это ровно то, что даёт HASH. `user_id` не имеет осмысленного порядка, поэтому RANGE по нему дал бы партиции случайного размера.                                                                                                    |
| **D.** Заказы, аналитика почти всегда работает с `created_at BETWEEN ...`         | **RANGE по `created_at`**   | Диапазонный запрос — единственный случай, где pruning отсекает партиции по границам. HASH здесь противопоказан: он разрушает порядок, и `BETWEEN` вынужден просматривать все партиции.                                                                                               |
| **E.** Платежи, разделение по странам (EE, LV, LT, FI, SE)                        | **LIST по стране**          | Конечный дискретный набор значений, каждое явно закреплено за партицией. Дополнительный довод: такое разбиение позволяет физически разнести данные разных юрисдикций — требование, которое встречается в платёжных системах. Стоит добавить DEFAULT на случай выхода на новый рынок. |

Общий принцип, который виден из таблицы: **стратегию определяет не структура данных, а форма запросов и операций обслуживания.** Одни и те же события можно разбить и по дате, и по хешу — вопрос в том, нужно ли вам удалять старое пачками (RANGE) или ровно распределять нагрузку (HASH).

## Часть 8. Партиционирование и индексы

```sql
CREATE INDEX idx_events_user_id ON events (user_id);
```

**До создания индекса:**

```
 Seq Scan on events_2026_09_10 events  (actual time=2.098..13.949 rows=7 loops=1)
   Filter: ((created_at >= '2026-09-10') AND (created_at < '2026-09-11') AND (user_id = 29064))
   Rows Removed by Filter: 99938
   Buffers: shared hit=860
```

**После:**

```
 Bitmap Heap Scan on events_2026_09_10 events  (actual time=0.065..0.104 rows=7 loops=1)
   Recheck Cond: (user_id = 29064)
   Filter: ((created_at >= '2026-09-10') AND (created_at < '2026-09-11'))
   Heap Blocks: exact=7
   Buffers: shared hit=10 read=2
   ->  Bitmap Index Scan on events_2026_09_10_user_id_idx  (actual time=0.048..0.048 rows=7 loops=1)
         Index Cond: (user_id = 29064)
```

| Метрика                     | До         | После               |
| --------------------------- | ---------- | ------------------- |
| Партиций просмотрено        | 1 из 3     | 1 из 3              |
| Тип доступа внутри партиции | `Seq Scan` | `Bitmap Index Scan` |
| Rows Removed by Filter      | **99 938** | **0**               |
| Buffers                     | **860**    | **12**              |
| Execution Time              | 13.949 ms  | **0.104 ms**        |

### Ответы

**1. Какие партиции были отфильтрованы через partition pruning?**

`events_2026_09_09` и `events_2026_09_11` — обе исключены по условию на `created_at`. В плане они отсутствуют полностью, остался единственный узел по `events_2026_09_10`.

**2. Используется ли индекс?**

Да: `Bitmap Index Scan on events_2026_09_10_user_id_idx`. Условие `user_id = 29064` перешло из `Filter` в `Index Cond` — то есть проверяется внутри индекса, и лишние строки из таблицы больше не читаются. Строка `Rows Removed by Filter: 99938` из плана исчезла.

**3. На каком уровне существует индекс?**

На обоих — и это важная деталь. Команда была одна, а индексов создалось четыре:

```
           indexname           |     tablename
-------------------------------+-------------------
 idx_events_user_id            | events              ← партиционированный индекс
 events_2026_09_09_user_id_idx | events_2026_09_09   ← дочерний
 events_2026_09_10_user_id_idx | events_2026_09_10   ← дочерний
 events_2026_09_11_user_id_idx | events_2026_09_11   ← дочерний
```

`idx_events_user_id` на родительской таблице — это **партиционированный индекс**: собственных данных он не хранит, а служит шаблоном и точкой управления. Реальные B-деревья живут в дочерних индексах, по одному на партицию.

Практическое следствие: при создании новой партиции PostgreSQL автоматически заводит для неё дочерние индексы по всем шаблонам родителя. Отдельно создавать их не нужно — это существенно упрощает job из части 10.

**4. Почему комбинация partitioning + index может быть эффективнее, чем один механизм?**

Потому что они сокращают работу на **разных уровнях**, и эффекты перемножаются:

```
3 партиции по 100 000 строк = 300 000 строк
        ↓ partition pruning по created_at
1 партиция — 100 000 строк          (в 3 раза меньше)
        ↓ индекс по user_id внутри партиции
7 строк                              (ещё в 14 000 раз меньше)
```

Каждый механизм в одиночку сделал бы лишь половину дела. Партиционирование без индекса дало бы `Seq Scan` по 100 000 строк с отбрасыванием 99 938 из них. Индекс без партиционирования пришлось бы применять к дереву втрое большего объёма, да ещё по всем трём партициям.

Есть и второй, менее очевидный выигрыш: **индекс на партиции меньше и мельче**. Дерево по 100 000 записей ниже, чем по 300 000, поэтому спуск к нужному значению короче. По той же причине дешевле обходятся обслуживающие операции — перестроить индекс одной партиции быстрее, чем один общий.

## Часть 9. Когда партиционирование не помогает

```sql
SELECT COUNT(*) FROM events WHERE event_type = 'click';
```

**До индекса** (план из части 2):

```
 Parallel Append  (actual time=0.014..20.028 rows=25068 loops=3)
   Buffers: shared hit=2582
   ->  Parallel Seq Scan on events_2026_09_09 ...  Rows Removed by Filter: 25013
   ->  Parallel Seq Scan on events_2026_09_10 ...
   ->  Parallel Seq Scan on events_2026_09_11 ...
 Execution Time: 31.585 ms
```

```sql
CREATE INDEX idx_events_event_type ON events (event_type);
```

**После:**

```
 Aggregate  (actual time=20.188..20.190 rows=1 loops=1)
   Buffers: shared hit=3 read=68
   ->  Append  (actual time=0.051..14.882 rows=75205 loops=1)
         ->  Index Only Scan using events_2026_09_09_event_type_idx on events_2026_09_09
               Index Cond: (event_type = 'click'::text)
               Heap Fetches: 0
         ->  Index Only Scan using events_2026_09_10_event_type_idx on events_2026_09_10
         ->  Index Only Scan using events_2026_09_11_event_type_idx on events_2026_09_11
 Execution Time: 20.190 ms
```

| Метрика              | Без индекса         | С индексом        |
| -------------------- | ------------------- | ----------------- |
| Партиций просмотрено | **3 из 3**          | **3 из 3**        |
| Тип доступа          | `Parallel Seq Scan` | `Index Only Scan` |
| Buffers              | **2582**            | **71**            |
| Execution Time       | 31.6 ms             | 20.2 ms           |

Индекс сократил чтение в 36 раз — но число просмотренных партиций осталось прежним: **все три**.

### Почему partitioning сам по себе не решил проблему этого запроса

Потому что `event_type` — не ключ партиционирования. Разбиение сделано по `created_at`, и про распределение типов событий схема ничего не знает. События с `event_type = 'click'` есть в каждом дне, значит и в каждой партиции — исключить ни одну планировщик не вправе.

Partition pruning работает не «умно», а строго формально: он отбрасывает партицию, только если из условия запроса **доказуемо** следует, что подходящих строк там нет. Такое доказательство даёт лишь условие по ключу партиционирования.

### Вывод: партиционирование отвечает на одну проблему, а индекс — на другую

|                       | Что сокращает                           | Чем управляется          | Когда бесполезно                 |
| --------------------- | --------------------------------------- | ------------------------ | -------------------------------- |
| **Партиционирование** | число просматриваемых **таблиц**        | ключом партиционирования | условие не по ключу              |
| **Индекс**            | число читаемых **строк внутри** таблицы | индексируемой колонкой   | результат — большая доля таблицы |

Это два независимых механизма, и подменять один другим нельзя:

- **Партиционирование** отвечает на вопрос «в каких физических кусках вообще могут лежать нужные строки». Плюс даёт то, чего индекс не умеет в принципе: мгновенное удаление старых данных через `DROP` партиции и обслуживание кусками.
- **Индекс** отвечает на вопрос «где именно внутри куска эти строки лежат».

В части 8 они сработали вместе и дали 860 → 12 буферов. В части 9 партиционирование оказалось бесполезным, а индекс — нет: 2582 → 71 буфер. Задача была индексная, и решалась она индексом.

## Часть 10. Автоматическое создание партиций

Реализовано в проекте, а не отдельным скриптом — партиции нужны работающему сервису, и следить за ними должен он сам.

| Файл                                        | Роль                                                    |
| ------------------------------------------- | ------------------------------------------------------- |
| `Repositories/PartitionRepository.cs`       | чтение системного каталога, `CREATE`/`DROP` партиций    |
| `Services/PartitionService.cs`              | расчёт ожидаемых партиций, поиск и создание недостающих |
| `BackgroundJobs/PartitionMaintenanceJob.cs` | периодический запуск                                    |
| `Controllers/PartitionsController.cs`       | ручной запуск для демонстрации                          |

### Как определяется, чего не хватает

Ключевая идея: **имя партиции однозначно выводится из её интервала**. `play_sessions_2026_09` — сентябрь 2026, `events_2026_09_14` — 14 сентября. Поэтому вопрос «какие партиции должны существовать» сводится к чистому вычислению от текущей даты и горизонта, а «каких не хватает» — к разности множеств.

```csharp
public List<ExpectedPartition> BuildExpected(PartitionTarget target, DateTime now)
{
    var result = new List<ExpectedPartition>();
    var start = Truncate(now, target.Granularity);

    for (var i = 0; i <= target.HorizonUnits; i++)
    {
        var from = Advance(start, target.Granularity, i);
        var to   = Advance(start, target.Granularity, i + 1);
        result.Add(new ExpectedPartition(BuildName(target, from), from, to));
    }
    return result;
}
```

Существующие партиции берутся из системного каталога — именно там PostgreSQL хранит связь родителя с дочерними таблицами:

```sql
SELECT child.relname
FROM pg_inherits i
JOIN pg_class  parent ON parent.oid = i.inhparent
JOIN pg_class  child  ON child.oid  = i.inhrelid
JOIN pg_namespace ns  ON ns.oid     = parent.relnamespace
WHERE ns.nspname = @Schema AND parent.relname = @Table;
```

## Часть 11. Production-сценарий: ночной job сломался

### PartitionHealthCheck

Проверка использует тот же расчёт ожидаемых партиций, что и job, но ничего не создаёт — только сравнивает:

```csharp
public async Task<PartitionHealthResult> CheckHealthAsync(PartitionTarget target, DateTime now)
{
    var expected = BuildExpected(target, now);
    var existing = await _repository.GetExistingPartitionsAsync(target.Schema, target.Table);

    return new PartitionHealthResult
    {
        Table   = target.FullName,
        Expected = expected.Select(e => e.Name).ToList(),
        Missing  = expected.Where(e => !existing.Contains(e.Name)).Select(e => e.Name).ToList(),
        CheckedAt = now
    };
}
```

`CRITICAL`, если отсутствует хотя бы одна ожидаемая партиция; иначе `OK`.

Порядок в фоновой job важен: **сначала создание, потом проверка**. Если job отработала штатно, проверка находит всё на месте и молчит. Алерт приходит ровно тогда, когда создание не сработало — то есть в той единственной ситуации, ради которой контроль и заводится.

### Подавление повторов

Дополнительное задание требует, чтобы один и тот же алерт не уходил бесконечно. Решение: уведомление отправляется не на каждую проверку, а **только при смене состояния**.

```
OK       → CRITICAL   отправить 🚨 alert
CRITICAL → CRITICAL   молчать
CRITICAL → OK         отправить 🟢 recovery
OK       → OK         молчать
```

```csharp
var wasHealthy = _lastKnownHealthy.TryGetValue(health.Table, out var previous) ? previous : true;

if (wasHealthy == health.IsHealthy)
    return false;                       // состояние не изменилось — не шлём

_lastKnownHealthy[health.Table] = health.IsHealthy;
var text = health.IsHealthy ? BuildRecoveryMessage(health) : BuildAlertMessage(health);
return await SendAsync(text);
```

Сервис зарегистрирован как singleton — иначе состояние терялось бы между запросами.

Telegram-бот. Токен и chat_id берутся из переменных окружения, которые `docker compose` подхватывает из `.env` в корне проекта; сам `.env` в репозиторий не попадает (`.gitignore`), рядом лежит `.env.example` с пустыми полями.

Если канал не настроен, сервис не падает: сообщение уходит в лог с предупреждением. Сбой доставки уведомления тоже не должен ронять приложение, поэтому отправка обёрнута в `try/catch`.

## Часть 12. Партиционирование собственной базы данных

### Шаги 1–4: выбор и обоснование

| Шаг       | Решение            |
| --------- | ------------------ |
| Таблица   | `play_sessions`    |
| Ключ      | `created_at`       |
| Стратегия | `RANGE`, помесячно |

**Почему именно эта таблица?**

Единственная в проекте, растущая неограниченно. Остальные ограничены сверху: `users`, `games`, `categories` — справочники; `game_categories` не может превысить произведения «игры × категории»; `user_games` ограничена тем же произведением, поскольку `PRIMARY KEY (user_id, game_id)` допускает одну строку на пару. У `play_sessions` такого предела нет — новая строка появляется при каждом запуске игры. На момент работы в ней 5 000 000 строк и 727 МБ вместе с индексами.

**Почему именно этот ключ?**

`created_at` — время события, по которому идут все диапазонные запросы сервиса: статистика за период, история за интервал, будущее удаление устаревших сессий. Альтернативы проигрывают: `user_id` дал бы равномерность, но сломал бы диапазонные запросы; `platform` имеет всего четыре значения и не годится в ключ разбиения.

**Почему именно эта стратегия?**

`RANGE` — единственная, при которой устаревшие данные можно удалить командой `DROP TABLE play_sessions_2024_09`: мгновенно, без чтения, без мусора и без нагрузки на журнал. При `HASH` сессии любого возраста равномерно размазаны по всем партициям, и удаление превратилось бы в построчный `DELETE` по всей таблице.

Помесячный шаг выбран как компромисс: посуточный дал бы за два года 730 партиций, что заметно утяжеляет планирование запросов; помесячный даёт 25 партиций по ~200 000 строк.

**Какие запросы должны получить пользу от pruning?**

`GET /api/stats/top-games` с параметром `days` и любые выборки сессий за период — они фильтруют ровно по `created_at`.

### Шаг 5: партиции

Создаются миграцией [`db/changelogs/009_partition_play_sessions.sql`](../db/changelogs/009_partition_play_sessions.sql).

Превратить обычную таблицу в партиционированную на месте PostgreSQL не умеет, поэтому миграция создаёт новую партиционированную таблицу, переливает данные и подменяет старую. Отдельная тонкость: **первичный ключ партиционированной таблицы обязан содержать ключ партиционирования**, поэтому `PRIMARY KEY (id)` стал `PRIMARY KEY (id, created_at)`.

Партиции создаются циклом по фактическому диапазону данных плюс три месяца вперёд:

```sql
DO $$
DECLARE lo date; hi date; m date;
BEGIN
    SELECT COALESCE(date_trunc('month', min(created_at))::date, date_trunc('month', now())::date),
           COALESCE(date_trunc('month', max(created_at))::date, date_trunc('month', now())::date)
      INTO lo, hi FROM play_sessions_legacy;

    hi := GREATEST(hi, (date_trunc('month', now()) + INTERVAL '3 months')::date);

    m := lo;
    WHILE m <= hi LOOP
        EXECUTE format(
            'CREATE TABLE IF NOT EXISTS %I PARTITION OF play_sessions FOR VALUES FROM (%L) TO (%L)',
            'play_sessions_' || to_char(m, 'YYYY_MM'), m, (m + INTERVAL '1 month')::date);
        m := (m + INTERVAL '1 month')::date;
    END LOOP;
END $$;
```

Результат — **28 партиций**, все 5 000 000 строк на месте:

```
       партиция        | count
-----------------------+--------
 play_sessions_2026_09 |  68002
 play_sessions_2026_08 | 208793
 play_sessions_2026_07 | 208937
 play_sessions_2026_06 | 208515
 ...
```

Любопытная деталь: `pg_total_relation_size('play_sessions')` возвращает **0 байт**. Родительская таблица не хранит данных вообще — она только маршрутизатор, а 727 МБ лежат в партициях.

**DEFAULT-партиция намеренно не создана.** Она принимала бы строки за пределами покрытого диапазона молча, и отсутствие будущих партиций осталось бы незамеченным. Здесь роль страховки играет `PartitionHealthCheck`: лучше получить алерт заранее, чем обнаружить забитую DEFAULT через полгода.

### Шаг 6: проверка запросов

| Запрос                                          | Эндпоинт                            | Партиций     | Buffers | Pruning  |
| ----------------------------------------------- | ----------------------------------- | ------------ | ------- | -------- |
| диапазон по `created_at`                        | `/api/stats/top-games?days=30`      | **1 из 28**  | 1694    | **да**   |
| `user_id` + `ORDER BY created_at DESC LIMIT 50` | `/api/users/{id}/sessions`          | **25 из 28** | 62      | **нет**  |
| `user_id` + диапазон дат                        | `/api/users/{id}/sessions?from=...` | несколько    | 41      | частично |

**Запрос 1** — ровно то, ради чего партиционирование делалось:

```
->  Parallel Seq Scan on play_sessions_2026_08 play_sessions
    (actual time=0.019..25.967 rows=104396 loops=2)
```

Одна партиция вместо двадцати восьми.

**Запрос 2 — неожиданный результат, который стоит проговорить.** Основная выборка сервиса фильтрует по `user_id` без условия на дату, а `user_id` не ключ разбиения. Pruning не срабатывает, и план открывает **25 отдельных Index Scan** — по одному на каждую партицию с данными — объединяя их через `Merge Append`.

Работает это по-прежнему быстро (62 буфера, 0.24 мс): `Merge Append` сливает уже отсортированные потоки и останавливается после пятидесятой строки благодаря `LIMIT`. Но плата реальна — двадцать пять открытий индекса вместо одного, и она растёт с числом партиций.

Честный вывод: **партиционирование по дате помогло статистике и диапазонным запросам, но слегка ухудшило самый частый запрос сервиса.** Это типичный компромисс, а не ошибка проектирования: выигрыш от `DROP` устаревших партиций и от статистики за период перевешивает. Если история пользователя станет узким местом, естественное решение — добавить в неё фильтр по времени, что для ленты сессий и так осмысленно.

### Шаги 7–9: автоматизация, контроль, alert

Реализованы теми же компонентами, что и части 10–11 — `play_sessions` просто добавлена в список наблюдаемых таблиц с помесячным шагом и горизонтом в 3 месяца. Отдельного кода для проекта не потребовалось.

Проверка на живой системе:

```

Partition job finished | table=public.play_sessions created=0
Partition check OK | table=public.play_sessions
```

# Контрольные вопросы

| №   | Вопрос                                                 | Ответ                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Что такое partitioning?                                | Разделение одной логической таблицы на несколько физических частей по значению ключа. Для приложения таблица остаётся одной: `INSERT` сам попадает в нужную партицию, `SELECT` читает из нужных.                                                                                                                                                                                                                                                                                                                               |
| 2   | Чем partitioning отличается от индекса?                | Сокращают работу на разных уровнях. Партиционирование уменьшает число просматриваемых **таблиц**, индекс — число читаемых **строк внутри** таблицы. Партиционирование даёт то, чего индекс не умеет: мгновенное удаление старых данных через `DROP` партиции.                                                                                                                                                                                                                                                                  |
| 3   | Какие стратегии поддерживает PostgreSQL?               | `RANGE` (диапазоны), `LIST` (перечисление значений), `HASH` (остаток от хеша). Плюс `DEFAULT`-партиция для RANGE и LIST.                                                                                                                                                                                                                                                                                                                                                                                                       |
| 4   | Когда использовать RANGE?                              | Когда у ключа есть естественный порядок и запросы работают с интервалами: время, цена, числовые диапазоны. Обязательна, если нужно удалять старые данные пачками.                                                                                                                                                                                                                                                                                                                                                              |
| 5   | Когда использовать LIST?                               | Когда значений мало, они дискретны и известны заранее: статус, тип клиента, страна, регион. Фильтрация идёт через `=` или `IN`.                                                                                                                                                                                                                                                                                                                                                                                                |
| 6   | Когда использовать HASH?                               | Когда нужна равномерность объёма, а не осмысленное разделение. Измерено: 4 партиции получили от 24.91% до 25.14% строк. Подходит как основа для будущего шардирования.                                                                                                                                                                                                                                                                                                                                                         |
| 7   | Как выбрать partition key?                             | По форме запросов и по операциям обслуживания, а не по структуре данных. Ключом должна быть колонка, по которой чаще всего идёт фильтрация, и та, по которой данные будут удаляться.                                                                                                                                                                                                                                                                                                                                           |
| 8   | Что такое partition pruning?                           | Исключение планировщиком партиций, в которых заведомо не может быть подходящих строк. Отдельной строкой в плане не отображается: проявляется тем, что ненужные партиции **вообще не появляются** в дереве плана.                                                                                                                                                                                                                                                                                                               |
| 9   | Почему pruning может не сработать?                     | Если условие идёт не по ключу партиционирования. Измерено: запрос по `created_at` прочитал 860 буферов из одной партиции, запрос по `event_type` — 2582 из всех трёх. Также pruning не работает, когда значение ключа неизвестно на этапе планирования.                                                                                                                                                                                                                                                                        |
| 10  | Можно ли использовать индексы вместе с partitioning?   | Да, и это обычная практика. `CREATE INDEX` на родительской таблице создаёт партиционированный индекс-шаблон и автоматически дочерние индексы на каждой партиции, включая будущие. Измерено: pruning плюс индекс дали 860 → 12 буферов.                                                                                                                                                                                                                                                                                         |
| 11  | Что произойдёт, если подходящей партиции нет?          | Вставка завершится ошибкой `no partition of relation ... found for row`. Это не деградация, а **полный отказ записи** — приложение начнёт падать на `INSERT`. Смягчается `DEFAULT`-партицией или контролем наличия партиций.                                                                                                                                                                                                                                                                                                   |
| 12  | Зачем создавать будущие партиции заранее?              | Потому что момент, когда партиция понадобится, наступает без предупреждения — с первой же вставкой за новую дату. Запас по горизонту даёт время заметить и починить сбой создания до того, как он затронет пользователей.                                                                                                                                                                                                                                                                                                      |
| 13  | Почему создание партиций должно быть автоматизировано? | Ручное создание — операция, о которой рано или поздно забудут, причём цена забывчивости это отказ записи. Плюс она регулярна и полностью детерминирована, то есть идеально подходит для автоматизации.                                                                                                                                                                                                                                                                                                                         |
| 14  | Чем логирование ошибки отличается от alerting?         | Лог пассивен: он фиксирует факт, но требует, чтобы кто-то в него заглянул. Alert активен — сам доставляет сообщение человеку. Запись в лог о непойманной проблеме обнаруживается обычно уже после того, как приложение начало падать.                                                                                                                                                                                                                                                                                          |
| 15  | Что такое recovery alert?                              | Уведомление о возврате системы в нормальное состояние. Без него получивший алерт не знает, решена проблема или всё ещё висит, и вынужден проверять вручную.                                                                                                                                                                                                                                                                                                                                                                    |
| 16  | Почему нельзя бесконечно отправлять одинаковый alert?  | Из-за усталости от оповещений: поток одинаковых сообщений перестают читать, и в нём теряются новые, действительно важные. Решение — отправлять только при смене состояния.                                                                                                                                                                                                                                                                                                                                                     |
| 17  | Всегда ли partitioning ускоряет запросы?               | Нет, и измерения это показали дважды. Запрос по `event_type` затронул все партиции, потому что фильтр не по ключу. Запрос истории пользователя после партиционирования стал открывать 25 индексов вместо одного. Партиционирование помогает только запросам по ключу разбиения.                                                                                                                                                                                                                                                |
| 18  | Какие проблемы при неправильном размере партиций?      | Слишком **мелкие**: сотни и тысячи партиций утяжеляют планирование — планировщик обязан рассмотреть каждую, — и раздувают системный каталог. Слишком **крупные**: партиция сама становится большой таблицей, и партиционирование не даёт выигрыша, а обслуживание одной партиции перестаёт быть быстрой операцией. Ориентир — партиция, сопоставимая по размеру с оперативной памятью сервера, и общее число партиций в пределах сотен. Для `play_sessions` выбран помесячный шаг: посуточный дал бы 730 партиций за два года. |
