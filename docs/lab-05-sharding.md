## Часть 1. Выбор данных для шардирования

### 1. Какую сущность выбрали

**`play_sessions`** — журнал игровых сессий. Та же таблица, что выступала растущей сущностью в предыдущих работах: на момент выполнения 5 000 000 строк, 727 МБ вместе с индексами, и рост ничем не ограничен.

Шардируют именно то, что перестаёт помещаться на один сервер. Справочники `users`, `games`, `categories` растут медленно, `user_games` ограничена произведением «пользователи × игры» — ни одна из них в шардировании не нуждается.

### 2. Какое поле используется как shard key

**`user_id`**.

### 3. Почему выбран именно этот ключ

Главный довод — **запросы сервиса фильтруют именно по нему**. `GET /api/users/{userId}/sessions` и `GET /api/users/{userId}/activity` начинаются с `WHERE user_id = ?`. При шардировании по `user_id` router сразу знает нужный сервер, и запрос обслуживает один шард.

Речь о свойстве, которое называют **локальностью**: связанные данные, читаемые вместе, должны попадать на один шард.

| Ключ          | Что произошло бы                                                                                                         |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **`user_id`** | все сессии одного пользователя на одном шарде, запрос идёт на один сервер                                                |
| `created_at`  | сессии одного пользователя разъехались бы по шардам (они происходили в разное время), история потребовала бы опроса всех |
| `id` сессии   | распределение ровное, но любой запрос по пользователю опрашивает все шарды                                               |
| `game_id`     | всего 1000 значений; популярные игры создали бы перекос                                                                  |

Отдельно стоит отметить, что ключ здесь **противоположен** ключу партиционирования из работы №3. Там разбиение шло по `created_at` — ради возможности удалять устаревшие данные целыми партициями через `DROP`. Здесь `created_at` плохой выбор именно потому, что запросы фильтруют не по нему. Одна таблица, разные механизмы, разные ключи — потому что задачи разные.

### 4. Насколько равномерно распределит

Ожидается ровное распределение. Пользователей около 20 000, сессии распределены между ними без резких перекосов, а хеш-функция дополнительно перемешивает значения. Прогноз — разброс в пределах процента; проверяется в части 4.

Известное ограничение такого ключа: в реальной системе появляется «тяжёлый» пользователь с непропорционально большим числом сессий, и его шард становится горячим. Шардирование по пользователю от этого не защищает.

### 5. Какие запросы сервиса используют этот ключ

| Эндпоинт                            | Запрос                                                          | Использует ключ |
| ----------------------------------- | --------------------------------------------------------------- | --------------- |
| `GET /api/users/{userId}/sessions`  | `WHERE ps.user_id = @UserId ... ORDER BY created_at DESC LIMIT` | да              |
| `GET /api/users/{userId}/activity`  | `WHERE u.id = @UserId ... GROUP BY`                             | да              |
| `POST /api/users/{userId}/sessions` | `INSERT ... VALUES (@UserId, ...)`                              | да              |
| `GET /api/stats/top-games`          | `GROUP BY ps.game_id` за период                                 | **нет**         |

Последняя строка важна: агрегат по всем пользователям ключ не использует, и при шардировании потребовал бы опроса всех шардов с последующей склейкой результатов. Это типичная плата за шардирование — запросы «поперёк ключа» становятся дороже.

`shard1` и `shard2` описаны так же и отличаются только тремя значениями:

|                  | shard0           | shard1           | shard2           |
| ---------------- | ---------------- | ---------------- | ---------------- |
| `container_name` | `gamelib_shard0` | `gamelib_shard1` | `gamelib_shard2` |

Отдельный том у каждого — именно это делает шарды независимыми. В отличие от реплики из работы №4, где данные являются копией Primary, здесь у каждого сервера своя доля.

### Запущенные экземпляры

```

gamelib_shard1  Up (healthy)  0.0.0.0:5442->5432/tcp
gamelib_shard2  Up (healthy)  0.0.0.0:5443->5432/tcp
```

```
shard0: таблиц=1
shard1: таблиц=1
shard2: таблиц=1
```

> **Подтверждает:** три независимых PostgreSQL запущены на разных портах, в каждом создана таблица `play_sessions`. Ни один из них не является репликой другого: общего хранилища нет, репликация между ними не настроена, запрос к одному ничего не знает о данных остальных.

### Проектное решение: схема шарда

Механизм работает так. Официальный образ PostgreSQL имеет точку входа `docker-entrypoint.sh`, которая при **пустом каталоге данных** выполняет всё, что лежит в `/docker-entrypoint-initdb.d/`. Файл [`db/sharding/init-shard.sql`](../db/sharding/init-shard.sql) смонтирован туда из проекта. В логе запуска это видно строкой:

```
/usr/local/bin/docker-entrypoint.sh: running /docker-entrypoint-initdb.d/init.sql
```

Важное следствие: скрипт **не выполняется повторно**. Изменить его и перезапустить контейнер недостаточно — нужно удалить том.

### Схема шарда

```sql
CREATE TABLE IF NOT EXISTS play_sessions (
    id               BIGINT      NOT NULL,
    user_id          INTEGER     NOT NULL,
    game_id          INTEGER     NOT NULL,
    duration_minutes INTEGER     NOT NULL,
    platform         VARCHAR(20) NOT NULL,
    created_at       TIMESTAMP   NOT NULL,
    PRIMARY KEY (id)
);

CREATE INDEX IF NOT EXISTS idx_shard_user_created
    ON play_sessions (user_id, created_at DESC);
```

Чего в схеме намеренно нет:

- **справочников `users` и `games`** — шардируется одна сущность, а не вся база;
- **внешних ключей** — PostgreSQL не умеет проверять целостность между разными серверами, за ней следит приложение. Это общее свойство шардирования, а не упрощение ради лабораторной.

## Часть 3. Реализация Router

Router отвечает на единственный вопрос: **на каком шарде лежит запись с таким ключом?**

### Хеш-функция

[`Services/Sharding/ShardHash.cs`](../Services/Sharding/ShardHash.cs)

```csharp
private const uint OffsetBasis = 2166136261;
private const uint Prime = 16777619;

public static uint Compute(string value)
{
    var hash = OffsetBasis;

    foreach (var b in Encoding.UTF8.GetBytes(value))
    {
        hash ^= b;          // подмешиваем очередной байт ключа
        hash *= Prime;      // умножение «размазывает» его по всему результату
    }

    return hash;
}

public static uint Compute(int shardKey) => Compute(shardKey.ToString());
```

**Почему не встроенный `GetHashCode()`.** В .NET хеш строк намеренно рандомизируется при каждом запуске процесса — защита от атак на хеш-таблицы. Для шардирования это означало бы катастрофу: после перезапуска сервиса `hash(42)` дал бы другое значение, записи «переехали» бы на другие шарды сами собой и перестали находиться.

Нужна функция, дающая одинаковый результат при любом запуске, на любой машине. Взят **FNV-1a** — простой, быстрый, хорошо перемешивающий. Умножение на простое число в цикле обеспечивает, что изменение одного байта ключа меняет весь хеш: соседние `user_id` попадают на разные шарды.

### Интерфейс

[`Services/Sharding/IShardRouter.cs`](../Services/Sharding/IShardRouter.cs)

```csharp
public interface IShardRouter
{
    string Strategy { get; }      // название стратегии — для отчётов и логов
    int ShardCount { get; }       // сколько шардов сейчас
    int GetShard(int shardKey);   // главный метод: ключ → номер шарда
}
```

Интерфейс выделен не ради абстракции: в части 6 появится вторая реализация, и сравнивать стратегии можно будет на одних и тех же данных, подменив только её.

### Стратегия hash(key) % N

[`Services/Sharding/ModuloShardRouter.cs`](../Services/Sharding/ModuloShardRouter.cs)

```csharp
public int GetShard(int shardKey) => (int)(ShardHash.Compute(shardKey) % (uint)ShardCount);
```

Вся стратегия — одна строка. Разбор:

- `ShardHash.Compute(shardKey)` — превращает `user_id` в равномерно распределённое 32-битное число;
- `% (uint)ShardCount` — берёт остаток от деления, он всегда попадает в диапазон `0..N-1`, то есть в номера существующих шардов;
- хеш беззнаковый, поэтому отрицательных результатов не бывает и дополнительная проверка не нужна.

Стратегия распределяет ровно, работает мгновенно и ничего не хранит. Её слабое место проявляется только при изменении `N` — этому посвящена часть 5.

### Результат распределения

| Шард | Записей | Идеал | Отклонение |
|---|---|---|---|
| Shard 0 | 33 363 | 33 333 | +0.09% |
| Shard 1 | 33 038 | 33 333 | −0.89% |
| Shard 2 | 33 599 | 33 333 | +0.80% |

### Выводы

**Насколько равномерно распределились данные.** Очень ровно: максимальное отклонение от идеальной доли — **0.89%**. Прогноз из части 1 подтвердился.

Стоит отметить, что равномерность здесь достигнута дважды. Хеш-функция FNV-1a равномерно раскладывает `user_id` по трём остаткам, а сами пользователи имеют сопоставимое число сессий — в среднем около 250 при 20 000 пользователей.

**Есть ли заметный дисбаланс.** Нет. Разброс меньше процента объясняется тем, что распределяются не отдельные сессии, а **пользователи целиком**: все сессии одного человека уходят на один шард. Небольшое отклонение — следствие того, что у разных пользователей разное число сессий.

**Может ли такой дисбаланс стать проблемой.** В текущем виде — нет, но механизм его возникновения важен.

Шардирование по `user_id` не защищает от «тяжёлого» ключа. Если в системе появится пользователь с непропорционально большим числом сессий — корпоративный аккаунт, бот, интеграция, — все его данные окажутся на одном шарде, и тот станет горячим и по объёму, и по нагрузке. Перенести часть его сессий на другой шард нельзя: это нарушило бы правило router, и запросы перестали бы их находить.

Это известное ограничение, называемое проблемой горячего ключа. Лечится оно не выбором хеш-функции, а изменением ключа шардирования — например, составным `(user_id, период)` — ценой потери локальности.

### Замечание по реализации

Первая версия метода использовала Dapper со списком объектов. Выглядит как массовая вставка, но библиотека выполняет **отдельный `INSERT` на каждую запись** — 100 000 обращений к базе по очереди. Замер: **137 177 мс**.

Заменено на `COPY` — потоковую загрузку PostgreSQL: данные уходят одним потоком по открытому соединению. Тот же механизм использует `pg_dump` при восстановлении.

| Способ | Время на 100 000 записей |
|---|---|
| построчный `INSERT` через Dapper | 137 177 мс |
| `COPY` (`BeginBinaryImportAsync`) | **1 473 мс** |

Разница в 93 раза. Распределение при этом одинаковое — менялся только способ доставки данных.

### Отдельно: запись в несколько шардов не является транзакцией

Три шарда — независимые серверы без общего координатора. Если запись во второй шард упадёт после успешной записи в первый, откатить первую невозможно: `ROLLBACK` действует в пределах одного сервера.

В лабораторной это не проявляется, поскольку данные заливаются разово и без сбоев. Но само явление — **распределённые транзакции** — и есть главная причина, по которой шардирование стараются откладывать как можно дольше, предпочитая индексы, партиционирование и реплики.

## Часть 5. Добавление нового shard

Ничего не переносится физически: router пересчитывает, куда **должна** была бы лечь каждая из тех же 100 000 записей при четырёх шардах, и сравнивает со старым ответом.

```csharp
var before = CreateRouter(strategy, fromShards);   // hash % 3
var after  = CreateRouter(strategy, toShards);     // hash % 4

// Ключ «переехал», если старый и новый router дали разные номера шардов.
var moved = userIds.Count(uid => before.GetShard(uid) != after.GetShard(uid));
```

```bash
curl "http://localhost:5000/api/sharding/compare?from=3&to=4&limit=100000"
```

```json
{
    "strategy": "hash(key) % 3",
    "fromShards": 3,
    "toShards": 4,
    "totalKeys": 100000,
    "moved": 75197,
    "movedPercent": 75.2
}
```

### Результат

```
Всего записей:   100 000
Новый shard:     Shard 3

Изменили shard:   75 197   (75.2 %)
Не изменили:      24 803   (24.8 %)
```

### Почему добавление одного PostgreSQL требует перемещения такого объёма данных

Потому что `% 3` и `% 4` — **разные функции**, а не одна с поправкой. Остаток от деления зависит от делителя целиком, и смена делителя меняет ответ почти для всех чисел.

На конкретных значениях хеша:

| hash | `% 3` | `% 4` | Переехал? |
|---|---|---|---|
| 100 | 1 | 0 | да |
| 101 | 2 | 1 | да |
| 102 | 0 | 2 | да |
| 103 | 1 | 3 | да |
| 104 | 2 | 0 | да |
| 105 | 0 | 1 | да |

Запись остаётся на месте только при случайном совпадении двух остатков. Вероятность этого — примерно 1 из 4, отсюда и теоретические 75% переезжающих. Измерено 75.2% — совпадение с теорией.

Практические последствия такого переезда:

- 75% базы нужно физически перенести между серверами;
- на время переноса данные в двух местах сразу, и router не знает, где искать актуальные;
- либо система останавливается на время миграции, либо нужен сложный механизм двойной записи;
- добавление **второго** шарда к четырём потребует перенести ещё около 80%.

Именно эта проблема и делает `hash(key) % N` непригодным для систем, где число шардов может измениться.

## Часть 6. Реализация Consistent Hashing

### Принцип

```
hash(shard_key)
       ↓
точка на hash ring (кольцо значений 0 .. 2^32-1)
       ↓
ближайший shard по часовой стрелке
```

Ключевое отличие от `% N`: **позиции шардов на кольце не зависят от их количества**. Добавление шарда вставляет на кольцо новые точки и отрезает им часть чужих секторов. Переезжают только ключи, попавшие в эти куски; остальные остаются на месте, потому что их ближайший шард по кольцу не изменился.

### Реализация

[`Services/Sharding/ConsistentHashRouter.cs`](../Services/Sharding/ConsistentHashRouter.cs)

**Построение кольца:**

```csharp
private const int VirtualNodesPerShard = 100;

for (var shard = 0; shard < shardCount; shard++)
for (var vnode = 0; vnode < VirtualNodesPerShard; vnode++)
    points.Add((ShardHash.Compute($"shard-{shard}#{vnode}"), shard));

points.Sort((a, b) => a.Position.CompareTo(b.Position));
```

Позиция точки считается от строки `"shard-0#0"`, `"shard-0#1"` и так далее — то есть **только от имени шарда и номера точки**, но не от общего их количества. Именно поэтому появление четвёртого шарда не сдвигает точки первых трёх.

**Поиск шарда для ключа:**

```csharp
var keyPosition = ShardHash.Compute(shardKey);
var index = Array.BinarySearch(_ringPositions, keyPosition);

if (index < 0)
    index = ~index;              // точного совпадения нет — берём первую точку больше

if (index >= _ringPositions.Length)
    index = 0;                   // ключ за последней точкой — замыкаем на первую

return _ringShards[index];
```

Движение «по часовой стрелке» — это поиск первой точки, чей хеш не меньше хеша ключа. Массив отсортирован, поэтому поиск двоичный. Последняя проверка замыкает кольцо: ключ, оказавшийся за самой дальней точкой, уходит на первую.

### Зачем virtual nodes

Каждый шард представлен не одной точкой, а сотней. С одной точкой на шард распределение вышло бы рваным: сектора между тремя случайными точками сильно различаются по длине, и один шард мог бы получить половину кольца, а другой — десятую часть.

Сотня точек на шард усредняет длины секторов: каждый шард владеет множеством мелких кусков, разбросанных по кольцу, и суммарные доли выравниваются.

## Часть 7. Сравнение стратегий

Тот же эксперимент, те же 100 000 записей, переход 3 → 4 шарда.

```json
{
    "modulo": {
        "strategy": "hash(key) % 3",
        "moved": 75197,
        "movedPercent": 75.2
    },
    "consistent": {
        "strategy": "Consistent Hashing (3 шардов × 100 точек)",
        "moved": 18346,
        "movedPercent": 18.35
    }
}
```

### Результат

| | Перемещено |
|---|---|
| `hash(key) % N` | **75.2 %** |
| Consistent Hashing | **18.35 %** |

Разница более чем в четыре раза: 75 197 записей против 18 346.

### 1. Почему результаты отличаются

При `% N` смена делителя меняет ответ функции почти для всех ключей — старое и новое распределения между собой не связаны.

При Consistent Hashing позиции существующих шардов на кольце **не меняются**. Новый шард лишь вставляет свои точки и забирает часть секторов у соседей. Ключ переезжает только если оказался в отрезанном куске.

Принципиальное следствие: при `% N` записи переезжают **между всеми шардами** — с нулевого на второй, со второго на третий и так далее. При Consistent Hashing переезд возможен только **в сторону нового шарда**; между существующими не перемещается ни одна запись.

### 2. Почему Consistent Hashing уменьшает объём перемещаемых данных

Потому что новый шард забирает примерно `1/N` кольца, где `N` — новое количество шардов. При переходе 3 → 4 это около 25%, и остальные 75% остаются нетронутыми.

Измеренные 18.35% оказались даже меньше теоретических 25%. Причина — конечное число виртуальных узлов: сто точек нового шарда легли на кольцо так, что захватили меньше равной доли. Это не ошибка, а свойство метода: **Consistent Hashing даёт приблизительный баланс, а не точный**. Увеличение числа виртуальных узлов приближает результат к идеалу.

### 3. Что произойдёт при добавлении ещё одного shard

Переход 4 → 5 переместит примерно `1/5` данных, то есть около 20%. Дальше доля продолжит уменьшаться: 5 → 6 даст примерно 17%, 9 → 10 — около 10%.

При `% N` картина обратная: 4 → 5 потребует перенести порядка 80%, и с ростом числа шардов эта доля только растёт.

| Переход | `% N` | Consistent Hashing |
|---|---|---|
| 3 → 4 | ~75% | ~25% (измерено 18.35%) |
| 4 → 5 | ~80% | ~20% |
| 9 → 10 | ~90% | ~10% |

### 4. Что произойдёт при удалении shard

При Consistent Hashing удаление симметрично добавлению: точки исчезнувшего шарда убираются с кольца, и его ключи достаются следующим по часовой стрелке. Переезжают **только данные удалённого шарда**, остальные не трогаются.

При `% N` удаление так же разрушительно, как добавление: `% 4` → `% 3` снова перемешает почти всё.

Это делает Consistent Hashing пригодным не только для планового расширения, но и для реакции на отказ сервера.

## Часть 8. Итог

**Shard** — самостоятельный экземпляр базы данных, хранящий часть общего набора данных. В работе поднято три PostgreSQL, каждый со своим томом; между собой они не связаны и о существовании друг друга не знают.

**Shard key** — поле, по значению которого определяется, на каком шарде лежит запись. Для `play_sessions` выбран `user_id`, поскольку именно по нему фильтруют основные запросы сервиса: при таком ключе все сессии одного пользователя попадают на один шард, и запрос истории обслуживает один сервер вместо трёх.

**Router** нужен потому, что PostgreSQL о шардировании ничего не знает: три сервера для него — три посторонние базы. Вся логика распределения живёт в приложении, и router отвечает на единственный вопрос — «на каком шарде эта запись».

**`hash(key) % N`** считает хеш ключа и берёт остаток от деления на число шардов; остаток всегда попадает в диапазон `0..N-1`. Стратегия распределяет ровно — измеренный перекос на 100 000 реальных записей составил 0.89% — работает мгновенно и ничего не хранит.

**Проблема возникает при изменении `N`.** Остаток от деления зависит от делителя целиком, поэтому `% 3` и `% 4` дают разные ответы почти для всех ключей. Измерено: при переходе с трёх шардов на четыре **переехало 75.2%** записей. Добавление одного сервера из трёх потребовало бы перенести три четверти базы.

**Consistent Hashing решает эту проблему** тем, что позиции шардов на кольце не зависят от их количества: они считаются от имени шарда, а не от `N`. Новый шард лишь вставляет свои точки и отрезает часть чужих секторов. На тех же данных переехало **18.35%** вместо 75.2% — в четыре раза меньше. Существенно и то, что между существующими шардами не перемещается ни одна запись: движение возможно только в сторону нового.

**Для своего сервиса я выбрал бы Consistent Hashing**, и причина не в разнице процентов самой по себе. Число шардов — величина, которая обязательно изменится: `play_sessions` растёт неограниченно, и расширение это вопрос времени. При `% N` каждое такое расширение означает остановку сервиса или сложный механизм двойной записи; при Consistent Hashing переносится обозримая доля, и остальные шарды работают как работали. Та же логика применима к отказу сервера — там `% N` перемешал бы всё, а кольцо отдаёт данные упавшего шарда соседям, не трогая остальных.

Плата за это — усложнение router: вместо одной операции взятия остатка появляются кольцо, двоичный поиск и виртуальные узлы. На фоне стоимости миграции трёх четвертей базы такая цена выглядит приемлемой.

# Вопросы для самопроверки

| № | Вопрос | Ответ |
|---|---|---|
| 1 | Что такое shard? | Самостоятельный экземпляр базы, хранящий часть общего набора данных. В работе — три PostgreSQL, каждый со своим томом, без репликации и общего хранилища между ними. В отличие от реплики, где у каждого сервера полная копия, у шарда только своя доля. |
| 2 | Что такое shard key? | Поле, по значению которого определяется расположение записи. Выбран `user_id`. Выбор диктуется тем, как фильтруют запросы: при `WHERE user_id = ?` router сразу знает нужный сервер. |
| 3 | Почему нельзя просто случайно распределять записи между PostgreSQL? | Потому что распределение должно быть **воспроизводимым**: записав строку на случайный сервер, её потом негде искать — пришлось бы опрашивать все. Распределение обязано быть функцией от ключа, дающей один и тот же ответ при каждом вызове. По этой же причине нельзя использовать `string.GetHashCode()` в .NET: он рандомизируется при каждом запуске процесса, и после перезапуска сервиса записи перестали бы находиться. |
| 4 | Как работает `hash(key) % N`? | Ключ превращается в число хеш-функцией, затем берётся остаток от деления на количество шардов. Остаток всегда лежит в диапазоне `0..N-1` — ровно номера существующих шардов. Хеш нужен, чтобы сгладить неравномерность самих ключей: последовательные `user_id` после FNV-1a дают совершенно разные значения. |
| 5 | Почему изменение количества shard'ов является проблемой? | Остаток от деления зависит от делителя целиком, поэтому `% 3` и `% 4` — разные функции, а не одна с поправкой. Запись остаётся на месте лишь при случайном совпадении остатков, вероятность чего около 1 из 4. Измерено: **75.2%** записей меняют шард при переходе 3 → 4. На время переноса данные оказываются в двух местах, и router не знает, где актуальные. |
| 6 | Что такое Consistent Hash Ring? | Кольцо значений от 0 до 2³²−1, на которое нанесены точки шардов. Ключ тоже превращается в точку, и запись уходит на первый шард по часовой стрелке. Позиции точек считаются от имени шарда (`"shard-0#17"`), а не от их количества — в этом всё отличие от `% N`. |
| 7 | Почему при добавлении shard'а не приходится переносить все данные? | Потому что точки существующих шардов на кольце не сдвигаются. Новый шард лишь вставляет свои точки и забирает примерно `1/N` кольца у соседей. Переезжают только ключи, попавшие в отрезанные куски; между существующими шардами не перемещается ничего. Измерено: 18.35% против 75.2% у `% N`. |
| 8 | Что такое virtual nodes и зачем они нужны? | Представление одного шарда множеством точек на кольце вместо одной — в реализации по 100 на шард. С одной точкой сектора между тремя случайными позициями сильно различались бы по длине, и один шард мог бы получить половину кольца, а другой — десятую часть. Множество мелких точек усредняет длины секторов и выравнивает доли. |
| 9 | Может ли Consistent Hashing гарантировать идеальное распределение нагрузки? | **Нет**, и это видно по измерениям. Теоретически новый шард должен забрать `1/4` кольца, то есть 25%; фактически он захватил **18.35%**. Причина в конечном числе виртуальных узлов: сто точек легли на кольцо не идеально ровно. Увеличение их числа приближает результат к теоретическому, но точного равенства не даёт никогда. Кроме того, равномерность распределения **ключей** не означает равномерности **нагрузки**: один ключ может оказаться в тысячи раз активнее прочих. |
| 10 | Что произойдёт, если один shard станет значительно более загруженным остальных? | Он превратится в узкое место: упрётся в диск или процессор, пока остальные простаивают, и вся система будет ограничена его пропускной способностью. Смысл шардирования при этом теряется — платите за три сервера, получаете производительность полутора.<br><br>Типичная причина — «горячий ключ»: пользователь-бот с сотнями тысяч сессий против средних 250. Разделить его данные между шардами нельзя: router считает `hash(user_id)` и пойдёт только в один сервер, остальное просто не найдёт.<br><br>Лечится либо сменой ключа на составной — например `(user_id, месяц)`, что размазывает тяжёлого пользователя по шардам ценой потери локальности, — либо таблицей исключений в router, где для единичных тяжёлых ключей действует отдельное правило, а остальные 99% запросов работают как прежде. |
