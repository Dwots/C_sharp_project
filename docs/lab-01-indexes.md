## Часть 2. Знакомство с EXPLAIN

### Задание 3. EXPLAIN

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 123;
```

```
 Gather  (cost=1000.00..17037.43 rows=11 width=53)
   Workers Planned: 2
   ->  Parallel Seq Scan on orders  (cost=0.00..16036.33 rows=5 width=53)
         Filter: (user_id = 123)
```

**1. Какой план выбрал PostgreSQL?**
Параллельное последовательное сканирование. Индексов по `user_id` нет, поэтому единственный доступный способ — прочитать таблицу целиком. Таблица достаточно велика (10 828 страниц), чтобы планировщик счёл выгодным подключить два фоновых воркера: узел `Gather` собирает их результаты в один поток.

**2. Какой тип сканирования используется?**
`Parallel Seq Scan` с условием в виде `Filter`. Важное отличие от `Index Cond`: `Filter` применяется **после** чтения строки с диска — то есть строка сначала поднимается в память, и только потом проверяется и, скорее всего, выбрасывается.

**3. Как PostgreSQL планирует найти строки?**
Прочитать все 1 000 000 строк и оставить те, где `user_id = 123`. Оценка `rows=11` взята не из данных, а из статистики: планировщик знает число различных значений `user_id` (`n_distinct`) и делит на него общее число строк.

### Задание 4. EXPLAIN ANALYZE

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 123;
```

```
 Gather  (cost=1000.00..17037.43 rows=11 width=53) (actual time=4.776..43.244 rows=9 loops=1)
   Workers Planned: 2
   Workers Launched: 2
   ->  Parallel Seq Scan on orders  (cost=0.00..16036.33 rows=5 width=53)
                                    (actual time=11.931..33.907 rows=3 loops=3)
         Filter: (user_id = 123)
         Rows Removed by Filter: 333330
 Planning Time: 0.892 ms
 Execution Time: 43.412 ms
```

| Показатель             | Значение                           |
| ---------------------- | ---------------------------------- |
| Тип сканирования       | `Parallel Seq Scan`                |
| Planning Time          | 0.892 ms                           |
| Execution Time         | 43.412 ms                          |
| Actual Rows            | 9 (по 3 на каждый из 3 процессов)  |
| Rows Removed by Filter | 333 330 на процесс ≈ 999 990 всего |
| Estimated Rows         | 11                                 |

Соотношение показательно: чтобы вернуть **9** строк, прочитано и отброшено **999 990**. Доля полезной работы составляет 0,0009% от выполненной.

**1. Чем `EXPLAIN` отличается от `EXPLAIN ANALYZE`?**
`EXPLAIN` только строит план и печатает оценки планировщика — запрос не выполняется. `EXPLAIN ANALYZE` реально выполняет запрос и добавляет к каждому узлу фактические значения: `actual time`, `actual rows`, `loops`, `Rows Removed by Filter`. Отсюда и появляются строки `Planning Time` / `Execution Time`, которых в обычном `EXPLAIN` нет.

**2. Почему `EXPLAIN ANALYZE` может выполняться значительно дольше?**
Потому что запрос выполняется фактически: производится чтение с диска, фильтрация, сортировка. К этому добавляются накладные расходы на инструментирование — замер времени на каждом узле и каждой итерации. Следует учитывать, что `EXPLAIN ANALYZE` на `INSERT`/`UPDATE`/`DELETE` **реально изменит данные**; чтобы этого избежать, его оборачивают в транзакцию с `ROLLBACK`.

**3. Чем отличаются estimated и actual rows?**
`estimated` — предсказание на основе статистики из `pg_statistic`, собранной последним `ANALYZE`. `actual` — сколько строк узел вернул на самом деле. Здесь 11 против 9.

## Часть 3. Sequential Scan

### Задание 5. Последовательное сканирование

```sql
EXPLAIN ANALYZE SELECT * FROM orders;
```

```
 Seq Scan on orders  (cost=0.00..20828.00 rows=1000000 width=53)
                     (actual time=0.009..81.465 rows=1000000 loops=1)
 Execution Time: 122.822 ms
```

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE amount > 0;
```

```
 Seq Scan on orders  (cost=0.00..23328.00 rows=999900 width=53)
                     (actual time=0.029..174.420 rows=999998 loops=1)
   Filter: (amount > '0'::numeric)
   Rows Removed by Filter: 2
 Execution Time: 214.764 ms
```

**1. Какой тип сканирования используется?**
`Seq Scan` в обоих случаях. Здесь он уже **не параллельный** — возвращается почти вся таблица, и накладные расходы на запуск воркеров и сборку результата не окупаются.

**2. Почему PostgreSQL выбирает Sequential Scan?**
В первом запросе нет условия вообще — нужны все строки, любой индекс был бы лишним посредником. Во втором условие `amount > 0` истинно для 999 998 строк из 1 000 000. Даже будь индекс по `amount`, обход через него означал бы: прочитать почти весь индекс, а затем всё равно поднять почти все страницы таблицы — но уже в случайном порядке вместо последовательного.

**3. Всегда ли Sequential Scan является плохим решением?**
Нет. Это плохой знак только тогда, когда запрос возвращает малую долю таблицы. Здесь `Seq Scan` — оптимальный план, и никакой индекс его не улучшит.

**Вывод: в каких случаях последовательное сканирование эффективнее индекса?**

- Когда запрос возвращает существенную долю таблицы (на таблице `orders` граница проходит между 50% и 75%). Индексный доступ читает страницы в случайном порядке, последовательный — подряд, а последовательное чтение кратно дешевле и для диска, и для упреждающего чтения ОС.
- Когда таблица мала и целиком помещается в несколько страниц: обращение к индексу добавит больше работы, чем сэкономит.
- Когда условия нет вовсе или оно неселективно.
- Когда нужен именно полный проход — агрегат по всей таблице, экспорт, `VACUUM FULL`.

## Часть 4. Первый индекс

### Задание 6. B-tree индекс

```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);
ANALYZE orders;
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 123;
```

```
 Bitmap Heap Scan on orders  (cost=4.51..47.60 rows=11 width=53)
                             (actual time=0.081..0.169 rows=9 loops=1)
   Recheck Cond: (user_id = 123)
   Heap Blocks: exact=9
   ->  Bitmap Index Scan on idx_orders_user_id  (cost=0.00..4.51 rows=11 width=0)
                                                (actual time=0.060..0.061 rows=9 loops=1)
         Index Cond: (user_id = 123)
 Planning Time: 1.092 ms
 Execution Time: 0.354 ms
```

| Метрика                       | До индекса                             | После индекса                            |
| ----------------------------- | -------------------------------------- | ---------------------------------------- |
| Тип Scan                      | `Parallel Seq Scan`                    | `Bitmap Heap Scan` + `Bitmap Index Scan` |
| Execution Time                | 43.412 ms                              | **0.354 ms**                             |
| Количество обработанных строк | 1 000 000 (999 990 отброшено фильтром) | 9 (прочитано 9 страниц)                  |
| Используемый индекс           | —                                      | `idx_orders_user_id`                     |
| Размер индекса                | —                                      | 9088 kB                                  |

**1. Изменился ли план выполнения?**
План изменился полностью. `Filter` заменён на `Index Cond`, и это принципиальное различие: условие применяется **внутри индекса**, до обращения к таблице, поэтому не подходящие строки не читаются вовсе, а не читаются с последующим отбрасыванием. Строка `Rows Removed by Filter` из плана исчезла.

**2. Использует ли PostgreSQL созданный индекс?**
Да. Причём вместо ожидаемого `Index Scan` выбран `Bitmap Index Scan` — стоимости двух вариантов оказались почти равны (47.60 против 48.62), и планировщик выбрал битмап с минимальным перевесом. При принудительном `SET enable_bitmapscan = off` получаем обычный `Index Scan` за 0.208 ms — то есть на практике он здесь даже чуть быстрее. Разница в пределах погрешности; важно, что оба варианта на два порядка лучше `Seq Scan`.

**3. Насколько изменилось время выполнения?**
43.412 ms → 0.354 ms, ускорение примерно в **123 раза**. Объём чтения упал с 10 828 страниц до 9.

Цена: индекс занимает 9 MB — около 10% от размера самой таблицы.

## Часть 5. Индекс используется не всегда

### Задание 7. Индекс и низкая селективность

```sql
CREATE INDEX idx_orders_status ON orders(status);
ANALYZE orders;
```

| `status`    | Строк   | % таблицы | Тип Scan         | Execution Time |
| ----------- | ------- | --------- | ---------------- | -------------- |
| `NEW`       | 249 955 | 25.00%    | Bitmap Heap Scan | 74.115 ms      |
| `PAID`      | 249 078 | 24.91%    | Bitmap Heap Scan | 64.919 ms      |
| `DELIVERED` | 250 502 | 25.05%    | Bitmap Heap Scan | 61.582 ms      |
| `CANCELLED` | 250 465 | 25.05%    | Bitmap Heap Scan | 70.934 ms      |

**1. Во всех ли случаях PostgreSQL использует индекс?**
На этих четырёх значениях — да, но не в виде `Index Scan`, а через `Bitmap`. Данные сгенерированы равномерно, поэтому все четыре запроса одинаковы по селективности (~25%) и получают одинаковый план. Чтобы увидеть отказ от индекса, нужно условие пошире:

| Условие                    | Доля таблицы | План             | Execution Time |
| -------------------------- | ------------ | ---------------- | -------------- |
| `status = 'NEW'`           | 25%          | Bitmap Heap Scan | 74.1 ms        |
| `status IN ('NEW','PAID')` | 50%          | Bitmap Heap Scan | 106.9 ms       |
| `status <> 'PAID'`         | **75%**      | **Seq Scan**     | 141.4 ms       |

Точка переключения на таблице `orders` лежит между 50% и 75%.

**2. Почему PostgreSQL может выбрать Sequential Scan, несмотря на наличие индекса?**
Потому что решение принимается по стоимости, а не по факту существования индекса. Для `status <> 'PAID'` оценка `Seq Scan` — 23328, и любой план через индекс дороже: пришлось бы прочитать три четверти индекса, а затем всё равно поднять почти все страницы таблицы, причём в случайном порядке. Индекс здесь — чистая дополнительная работа.

**3. Как количество возвращаемых строк влияет на выбор плана?**
Напрямую. Чем больше доля возвращаемых строк, тем менее выгоден индекс: растёт число обращений к куче, и случайное чтение проигрывает последовательному. Порог зависит от `random_page_cost` / `seq_page_cost`, от ширины строки и от физической упорядоченности данных (`correlation` в `pg_stats`).

## Часть 6. Селективность

### Задание 8. Исследование распределения данных

```sql
SELECT status, COUNT(*) AS rows,
       ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 2) AS pct
FROM orders GROUP BY status ORDER BY rows;
```

```
  status   |  rows  |  pct
-----------+--------+-------
 PAID      | 249078 | 24.91
 NEW       | 249955 | 25.00
 CANCELLED | 250465 | 25.05
 DELIVERED | 250502 | 25.05
```

Сводка по всем измеренным условиям:

| Условие                        | Строк   | Доля    | План                | Execution Time |
| ------------------------------ | ------- | ------- | ------------------- | -------------- |
| `user_id = 123`                | 9       | 0.0009% | Bitmap / Index Scan | 0.354 ms       |
| `created_at > NOW() - 1 day`   | 1 369   | 0.14%   | Bitmap Heap Scan    | 6.502 ms       |
| `created_at > NOW() - 7 days`  | 9 722   | 0.97%   | Bitmap Heap Scan    | 15.361 ms      |
| `created_at > NOW() - 1 month` | 41 850  | 4.19%   | Bitmap Heap Scan    | 30.124 ms      |
| `status = 'NEW'`               | 249 955 | 25.00%  | Bitmap Heap Scan    | 74.115 ms      |
| `created_at > NOW() - 1 year`  | 500 867 | 50.09%  | **Seq Scan**        | 299.457 ms     |
| `status <> 'PAID'`             | 750 922 | 75.09%  | **Seq Scan**        | 141.380 ms     |

**Вывод: как селективность условия влияет на эффективность индекса?**

Селективность — доля строк, проходящих условие, — определяет всё. Зависимость не линейная, а с явным переломом:

- **до ~1%** — индекс даёт выигрыш в десятки и сотни раз (`user_id = 123`: 123×);
- **1–25%** — индекс ещё выигрывает, но эффект тает: при 25% (`status = 'NEW'`) `Bitmap Heap Scan` читает `Heap Blocks: exact=10828` — то есть **все 10 828 страниц таблицы**. Каждая случайно взятая четверть строк задевает практически каждую страницу. Выигрыш остаётся только на процессорной стоимости фильтрации, не на объёме чтения;
- **свыше ~50%** — индекс становится вреден, планировщик от него отказывается.

Отсюда практическое правило: индекс имеет смысл на колонке с высокой кардинальностью (`user_id`, `email`, `created_at`) и почти бесполезен на колонке-перечислении с несколькими равновероятными значениями (`status`, `platform`, `is_active`). Для последних выручает частичный индекс — но только если нужное значение действительно редкое.

**До создания индекса**, `created_at > NOW() - INTERVAL '7 days'`:

```
 ->  Parallel Seq Scan on orders  (cost=0.00..18119.67 rows=3932 width=53)
                                  (actual time=0.065..110.308 rows=3241 loops=3)

```

```sql
CREATE INDEX idx_orders_created_at ON orders(created_at);

```

**После**, по разным диапазонам:

| Диапазон | Строк   | Доля   | Тип Scan         | Execution Time               |
| -------- | ------- | ------ | ---------------- | ---------------------------- |
| 1 day    | 1 369   | 0.14%  | Bitmap Heap Scan | 6.502 ms                     |
| 7 days   | 9 722   | 0.97%  | Bitmap Heap Scan | **15.361 ms** (было 121.882) |
| 1 month  | 41 850  | 4.19%  | Bitmap Heap Scan | 30.124 ms                    |

**1. Во всех ли случаях PostgreSQL использует индекс?**
Нет. На диапазонах до месяца включительно — использует. На годе, где под условие попадает половина таблицы, переключается на `Seq Scan` и полностью игнорирует созданный индекс.

**2. Как размер временного диапазона влияет на план?**
Диапазон напрямую задаёт селективность. Узкое окно = мало строк = индекс выгоден. Расширение окна двигает запрос по той же кривой селективности, пока стоимость индексного доступа не превысит стоимость полного прохода.

На семи днях выигрыш восьмикратный (121.882 → 15.361 ms), хотя оба плана читают одну и ту же таблицу: `Seq Scan` поднимал все 10 828 страниц ради 9 722 строк, а `Bitmap` — только те страницы, где эти строки лежат.

**3. В какой ситуации использование индекса становится менее выгодным?**
Когда окно расширяется настолько, что задевает большинство страниц. Практический вывод для реального сервиса: запросы вида «за последние сутки/неделю» индекс по времени ускоряет отлично, а отчёты «за всё время» им не ускорить.

## Часть 8. Bitmap Scan

### Задание 10. Bitmap Index Scan

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE status = 'NEW';
```

```
 Bitmap Heap Scan on orders  (cost=2827.88..16816.29 rows=252833 width=53)
                             (actual time=10.519..59.125 rows=249955 loops=1)
   Recheck Cond: ((status)::text = 'NEW'::text)
   Heap Blocks: exact=10828
   Buffers: shared hit=11041
   ->  Bitmap Index Scan on idx_orders_status  (cost=0.00..2764.67 rows=252833 width=0)
                                               (actual time=8.343..8.344 rows=249955 loops=1)
         Index Cond: ((status)::text = 'NEW'::text)
         Buffers: shared hit=213
 Planning Time: 1.220 ms
 Execution Time: 71.003 ms
```

**1. Что делает Bitmap Index Scan?**
Проходит по индексу и вместо того, чтобы сразу лезть в таблицу за каждой найденной строкой, строит в памяти битовую карту — отметки, какие страницы кучи содержат подходящие строки. Таблицу он не трогает вообще: по `Buffers: shared hit=213` видно, что прочитано всего 213 страниц — это сам индекс. Результат получается **отсортированным по физическому расположению**, а не по значению ключа.

**2. Что делает Bitmap Heap Scan?**
Берёт готовую битовую карту и читает отмеченные страницы кучи **по возрастанию номера** — то есть превращает случайный доступ в близкий к последовательному. `Heap Blocks: exact=10828` показывает, сколько страниц он поднял.

Строка `Recheck Cond` имеет практическое значение: если строк слишком много, битовая карта переходит из точного режима (`exact`) в приблизительный (`lossy`) — начинает помечать страницу целиком вместо отдельных строк, и тогда условие приходится перепроверять для каждой строки такой страницы. Здесь до этого не дошло — карта осталась `exact`.

**3. Почему Bitmap Scan вместо обычного Index Scan?**
`Index Scan` идёт по индексу и для каждой записи сразу прыгает в кучу. При 249 955 совпадениях это четверть миллиона случайных обращений, причём к одной и той же странице он может вернуться десятки раз. `Bitmap` читает каждую нужную страницу ровно один раз и в удобном для диска порядке. Поэтому bitmap — режим «средней» селективности: слишком много строк для `Index Scan`, слишком мало для `Seq Scan`.

Проверка от обратного: при `SET enable_bitmapscan = off` планировщик не переключается на `Index Scan`, а сразу выбирает `Seq Scan` (104.756 ms) — то есть обычный индексный проход здесь настолько дорог, что полное сканирование выгоднее.

**Ключевое наблюдение:** `Heap Blocks: exact=10828` в точности равно `relpages` таблицы. При 25% случайно разбросанных строк bitmap читает **всю таблицу до последней страницы** — и выигрывает у `Seq Scan` лишь за счёт того, что не тратит процессор на проверку условия для остальных 750 тысяч строк. Именно поэтому дальнейший рост доли (75%) окончательно переворачивает выбор в пользу `Seq Scan`.

## Часть 9. Несколько условий и несколько индексов

### Задание 11. Использование нескольких индексов

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 123 AND status = 'PAID';
```

```
 Bitmap Heap Scan on orders  (cost=4.51..47.62 rows=3) (actual time=0.101..0.101 rows=1 loops=1)
   Recheck Cond: (user_id = 123)
   Filter: ((status)::text = 'PAID'::text)
   Rows Removed by Filter: 8
   Heap Blocks: exact=9
   ->  Bitmap Index Scan on idx_orders_user_id  (actual time=0.030..0.031 rows=9 loops=1)
 Execution Time: 0.186 ms
```

**1. Использует ли PostgreSQL один индекс или несколько?**
Один — только `idx_orders_user_id`. Индекс по `status` существует, но не задействован: условие по нему стоит в `Filter`, то есть проверяется уже после чтения строк.

**2. Есть ли в плане `BitmapAnd`?**
Нет. Причина в селективности первого условия: `user_id = 123` возвращает 9 строк, лежащих в 9 страницах. Проверить `status` у девяти прочитанных строк — девять операций сравнения. Построение второй битовой карты потребовало бы прохода по 250 000 записям индекса ради экономии восьми страниц чтения, что заведомо дороже.

`BitmapAnd` возникает при других условиях: когда **оба** предиката по отдельности дают много строк, а их пересечение — мало, и за счёт этого резко сокращается число читаемых страниц. Для проверки подобран следующий запрос:

```sql
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE created_at > NOW() - INTERVAL '15 days'
  AND amount BETWEEN 1000 AND 1200;
```

```
 Bitmap Heap Scan on orders  (cost=801.82..2183.49 rows=408) (actual time=5.996..7.311 rows=408 loops=1)
   Recheck Cond: ((created_at > ...) AND (amount >= 1000) AND (amount <= 1200))
   Heap Blocks: exact=399
   ->  BitmapAnd  (cost=801.82..801.82 rows=408) (actual time=5.913..5.913 rows=0 loops=1)
         ->  Bitmap Index Scan on idx_orders_created_at  (actual rows=20316 loops=1)
         ->  Bitmap Index Scan on idx_orders_amount      (actual rows=19801 loops=1)
 Execution Time: 7.449 ms
```

Два дочерних узла строят свои карты — 20 316 и 19 801 строка, — `BitmapAnd` их пересекает, остаётся 408 строк в 399 страницах. Против ~9 000 страниц, которые пришлось бы поднять по любому из индексов поодиночке.

_(Для этого был добавлен `idx_orders_amount`)_

**3. Почему PostgreSQL может объединять результаты нескольких индексов?**
Потому что битовая карта — это множество адресов, а множества можно пересекать (`AND`) и объединять (`OR`). Обычный `Index Scan` так не умеет: он идёт по одному индексу и сразу лезет в таблицу. Битмап сначала собирает адреса целиком, и на этом промежуточном этапе с ними можно делать операции.

## Часть 10. Composite Index

### Задание 12. Составной индекс

```sql
CREATE INDEX idx_orders_user_status ON orders(user_id, status);
```

|                      | Два отдельных индекса       | Составной    |
| -------------------- | --------------------------- | ------------ |
| План                 | `Bitmap Heap Scan` + Filter | `Index Scan` |
| Cost                 | 47.62                       | **16.48**    |
| Прочитано из таблицы | 9 строк, 8 отброшено        | **1 строка** |
| Heap Blocks          | 9                           | —            |

Составной индекс убрал `Rows Removed by Filter`: оба условия проверяются внутри индекса, до обращения к таблице.

**1. Какой вариант оказался эффективнее?**

**Составной индекс.** Он выигрывает по всем измеримым показателям плана: стоимость 16.48 против 47.62, из таблицы читается одна строка вместо девяти, `Rows Removed by Filter` исчезает совсем.

Однако по **времени выполнения** превосходство не наблюдается. Каждый вариант выполнен по пять раз:

```
составной:     0.048  0.043  0.091  0.079  0.091 мс
два отдельных: 0.071  0.052  0.085  0.051  0.088 мс
```

Диапазоны значений полностью перекрываются, поэтому определить более быстрый вариант по этим измерениям невозможно.

Причина в масштабе задачи: девять строк целиком находятся в оперативной памяти, и восемь дополнительных чтений из кэша занимают доли микросекунды — меньше, чем разброс между отдельными запусками. Измерение упирается в собственную погрешность, а не в различие планов.

**Вывод: составной индекс эффективнее, что подтверждается планом выполнения, однако на данном объёме данных это преимущество лежит ниже порога измеримости.** Оно проявится при объёме, когда таблица перестанет помещаться в кэш и каждое дополнительное чтение будет означать обращение к диску.

**2. Всегда ли составной индекс лучше нескольких отдельных?**
Нет. У него два минуса.

Во-первых, он работает только для запросов, где ограничена его **первая** колонка: `(user_id, status)` бесполезен для запроса только по `status`.

Во-вторых, он дороже: 20 МБ против 9 МБ у `idx_orders_user_id`. Платить приходится и местом на диске, и замедлением каждой вставки — при `INSERT` обновляются все индексы таблицы.

Два отдельных индекса гибче: каждый обслуживает свои запросы и годится в `BitmapAnd`. Составной быстрее, но только на том сочетании условий, под которое сделан.

**3. От чего зависит выбор?**
От того, ходят ли эти условия вместе. Если `user_id` и `status` почти всегда в одном `WHERE` — составной. Если запросы бывают и по одному, и по другому порознь — отдельные.

## Часть 11. Порядок колонок в составном индексе

### Задание 13. Влияние порядка колонок

Создан индекс `idx_orders_user_created_at (user_id, created_at)`, после чего выполнены три запроса:

| Запрос                                         | Использован индекс                                  |
| ---------------------------------------------- | --------------------------------------------------- |
| `WHERE user_id = 123`                          | да, `(user_id, created_at)`                         |
| `WHERE user_id = 123 AND created_at > 30 days` | да, `Index Scan`, cost **8.45**                     |
| `WHERE created_at > 30 days`                   | **нет** — ушёл на отдельный `idx_orders_created_at` |

Чтобы исключить влияние запасного индекса и убедиться, что причина именно в порядке колонок, индекс `idx_orders_created_at` был удалён, а третий запрос повторён:

```
 ->  Parallel Seq Scan on orders  (cost=0.00..18119.67 rows=17437)
       Rows Removed by Filter: 319568
 Execution Time: 47.861 ms
```

Полное сканирование. Индекс `(user_id, created_at)` для запроса только по `created_at` **бесполезен полностью**.

Затем создан индекс с обратным порядком колонок — `idx_orders_created_at_user (created_at, user_id)`:

| Запрос                                     | Какой индекс выбран                    |
| ------------------------------------------ | -------------------------------------- |
| `WHERE user_id = 123`                      | `(user_id, created_at)`                |
| `WHERE user_id = 123 AND created_at > ...` | `(user_id, created_at)`                |
| `WHERE created_at > ...`                   | **`(created_at, user_id)`**, 16.824 мс |

Каждый индекс обслуживает те запросы, где ограничена его **первая** колонка.

**1. Как порядок колонок влияет на возможность использования индекса?**
Решающим образом. B-tree отсортирован сначала по первой колонке, а внутри одинаковых её значений — по второй. Структура аналогична телефонному справочнику, упорядоченному по фамилии, а внутри одинаковых фамилий — по имени: поиск «Иванова Петра» выполняется за несколько шагов, тогда как поиск всех Петров с произвольной фамилией требует полного перебора.

Правило: индекс `(A, B)` работает для условий по `A` и по `A + B`, но **не** для условий только по `B`.

**2. Почему `(user_id, created_at)` и `(created_at, user_id)` — разные индексы?**
Потому что это два разных порядка сортировки, физически два разных дерева. Первый группирует записи по пользователям, второй — по времени. Взаимозаменяемыми они не будут никогда.

**3. Какой индекс лучше под каждый запрос?**

| Запрос                 | Подходящий индекс                                                 |
| ---------------------- | ----------------------------------------------------------------- |
| только `user_id`       | `(user_id, ...)` — любой с `user_id` впереди                      |
| `user_id + created_at` | `(user_id, created_at)` — равенство по первой, диапазон по второй |
| только `created_at`    | `(created_at, ...)`                                               |

Общее правило: **колонки с равенством ставятся первыми, колонка с диапазоном — последней.** После диапазона индекс дальше не сужается, поэтому всё, что за ним, работать уже не будет.

## Часть 12. WHERE + ORDER BY

### Задание 14. Индекс и сортировка

Базовый замер (индекса `(user_id, created_at)` в этот момент нет):

```
 Sort  (cost=47.79..47.81 rows=11) (actual time=0.079..0.080 rows=9 loops=1)
   Sort Key: created_at DESC
   Sort Method: quicksort  Memory: 25kB
   ->  Bitmap Heap Scan on orders ...
 Execution Time: 0.137 ms
```

Операция `Sort` присутствует. Создаётся индекс, предусмотренный заданием:

```sql
CREATE INDEX idx_orders_user_created_at_desc ON orders(user_id, created_at DESC);
```

**Операция `Sort` из плана не исчезла.** Это наиболее неочевидный результат работы:

```
 Sort  (cost=47.79..47.81 rows=11) (actual time=0.144..0.145 rows=9 loops=1)
   Sort Key: created_at DESC
   ->  Bitmap Heap Scan on orders
         ->  Bitmap Index Scan on idx_orders_user_created_at_desc
```

Индекс используется — но через **Bitmap**. А битмап собирает все адреса и сортирует их по номерам страниц — то есть **уничтожает порядок индекса**. Упорядоченность теряется, и сортировать всё равно приходится.

Для проверки планировщик принудительно переводится на обычный `Index Scan`:

```sql
SET enable_bitmapscan = off;
```

```
 Index Scan using idx_orders_user_created_at_desc on orders  (cost=0.42..48.62 rows=11)
 Execution Time: 0.158 ms
```

`Sort` исчез.

**1. Исчезла ли операция Sort?**
Только при доступе через `Index Scan`. Через `Bitmap Heap Scan` — нет. Само по себе наличие подходящего индекса сортировку не убирает; нужно, чтобы планировщик выбрал упорядоченный способ чтения.

**2. Почему индекс может использоваться для сортировки?**
B-tree физически хранит записи в порядке ключа. Идя по нему подряд, строки получаются уже отсортированными — сортировать нечего. Причём индекс читается в обе стороны: для `ORDER BY created_at DESC` подойдёт и обычный ASC-индекс, просто читаться будет с конца — в плане это отображается как `Index Scan Backward`.

**3. Почему порядок колонок здесь важен?**
Индекс отдаёт строки, отсортированные по `created_at`, только **внутри одного `user_id`**. Есть равенство `user_id = 123` — все нужные строки лежат в одном непрерывном куске индекса, уже упорядоченные. Будь колонки наоборот, `(created_at, user_id)`, строки одного пользователя оказались бы разбросаны по всему индексу, и порядок пришлось бы восстанавливать сортировкой.

## Часть 13. Реальный API-запрос

### Задание 15. Pagination Query

Запрос в исходной формулировке, с `user_id = 123`, оказался непоказательным: у этого пользователя всего 9 заказов, и `LIMIT 20` не накладывает никакого ограничения. Поэтому измерен эквивалентный по смыслу запрос, в котором лимит действительно работает, — лента последних заказов:

```sql
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20;
```

**Без подходящего индекса** (планировщику запрещены индексные пути):

```
 Limit  (cost=27082.05..27084.38 rows=20) (actual time=69.290..73.782 rows=20 loops=1)
   ->  Sort  (cost=26082.03..27123.69 rows=416667)
         Sort Key: created_at DESC
         Sort Method: top-N heapsort  Memory: 29kB
         ->  Parallel Seq Scan on orders  (actual rows=333333 loops=3)
 Execution Time: 73.939 ms
```

**С индексом по `created_at`:**

```
 Limit  (cost=0.42..1.90 rows=20) (actual time=0.082..0.309 rows=20 loops=1)
   ->  Index Scan Backward using idx_orders_created_at_user on orders
       (cost=0.42..73704.02 rows=1000000) (actual time=0.080..0.304 rows=20 loops=1)
 Execution Time: 0.438 ms
```

| Метрика         | До                           | После                 |
| --------------- | ---------------------------- | --------------------- |
| Тип Scan        | `Parallel Seq Scan` + `Sort` | `Index Scan Backward` |
| Execution Time  | 73.939 ms                    | **0.438 ms**          |
| Прочитано строк | 1 000 000                    | **20**                |

**Ускорение в 168 раз.**

**Обоснование структуры индекса.** Ключевых наблюдения два.

Первое: `Sort Method: top-N heapsort` — PostgreSQL не сортирует весь миллион, а держит в памяти только 20 лучших. Оптимизация серьёзная, но она не спасает: **прочитать всё равно надо все строки**, иначе не узнать, какие двадцать самые свежие.

Второе: обратите внимание на оценку `Index Scan Backward` — `cost=0.42..73704.02`, то есть полная стоимость обхода миллиона строк. Но узел `Limit` сверху показывает `cost=0.42..1.90`: планировщик понимает, что после двадцатой строки чтение прекратится. Именно в этом весь смысл — индекс отдаёт строки **уже в нужном порядке**, поэтому первые двадцать и есть ответ, и до остальных дело не доходит.

Индекс здесь не «ускоряет поиск», а даёт возможность остановиться.

## Часть 14. Index Only Scan

### Задание 16. Получение данных из индекса

```sql
EXPLAIN ANALYZE SELECT id, user_id FROM orders WHERE user_id = 123;
```

**До** — обычный индекс по `user_id` не покрывает `id`, поэтому за ним приходится идти в таблицу:

```
 Bitmap Heap Scan on orders  (cost=4.51..47.60 rows=11)
 Execution Time: 0.160 ms
```

**После** создания покрывающего индекса:

```sql
CREATE INDEX idx_orders_user_id_include ON orders(user_id) INCLUDE (id, status, created_at);
VACUUM ANALYZE orders;
```

```
 Index Only Scan using idx_orders_user_id_include on orders  (cost=0.42..4.62 rows=11)
   Heap Fetches: 0
 Execution Time: 0.161 ms
```

Стоимость упала с 47.60 до **4.62** — в десять раз. `Heap Fetches: 0` означает, что к таблице не было **ни одного** обращения: весь ответ собран из индекса.

**1. Чем Index Only Scan отличается от обычного Index Scan?**
`Index Scan` находит в индексе адрес и идёт за строкой в таблицу. `Index Only Scan` в таблицу не ходит вообще — все нужные колонки уже лежат в самом индексе.

**2. Почему PostgreSQL может не обращаться к основной таблице?**
Потому что запрошенные колонки есть в индексе. Но одного этого мало: индекс не хранит информацию о видимости строк (какие транзакции их видят). Для этого используется **карта видимости** — если страница в ней помечена как «видима всем», проверять нечего.

Этим объясняется `VACUUM ANALYZE` перед замером: карту видимости обновляет именно `VACUUM`. Без него значение `Heap Fetches` было бы больше нуля — обращения к таблице для проверки видимости сохранились бы, и смысл покрывающего индекса терялся.

**3. Какие условия необходимы?**

- все колонки из `SELECT` и `WHERE` присутствуют в индексе;
- страницы помечены в карте видимости, то есть по таблице недавно проходил `VACUUM`.

**Про `INCLUDE`.** Колонки после `INCLUDE` хранятся только в листьях дерева и **не участвуют в сортировке**. Разница с `(user_id, id, status, created_at)` практическая: по `INCLUDE`-колонкам нельзя искать и нельзя сортировать, зато дерево остаётся компактнее и поиск по `user_id` не замедляется.

**Цена.** Индекс занял **52 МБ** — больше, чем сама таблица (85 МБ) на две трети. Он тащит в себе копию четырёх колонок. Покрывающие индексы — самые дорогие по месту.

## Часть 15. Partial Index

### Задание 17. Частичный индекс

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'NEW' ORDER BY created_at;
```

```
 Sort  (cost=47461.03..48082.03 rows=248400) (actual time=93.502..119.517 rows=249955)
   Sort Key: created_at
   Sort Method: external merge  Disk: 16184kB
   ->  Bitmap Heap Scan on orders ...
 Execution Time: ~120 ms
```

Отдельно стоит отметить `external merge Disk: 16184kB` — 250 тысяч строк не поместились в `work_mem`, и сортировка пошла через временный файл на диске.

```sql
CREATE INDEX idx_orders_new ON orders(created_at) WHERE status = 'NEW';
```

**Частичный индекс не был использован.** План не изменился вообще.

Причина в том, что на данных таблицы `orders` не выполняется исходная предпосылка «только небольшая часть заказов имеет статус NEW»: статусы распределены равномерно, и `NEW` — это 25% таблицы. Читать 250 тысяч строк через индекс в порядке `created_at` означало бы четверть миллиона случайных обращений к куче — дороже, чем битмап с последующей сортировкой.

Что индекс всё-таки дал — это экономию места:

| Индекс                           | Размер      |
| -------------------------------- | ----------- |
| Полный по `created_at`           | 21 MB       |
| Частичный `WHERE status = 'NEW'` | **5504 kB** |

Ровно вчетверо, пропорционально доле строк.

**Проверка на данных, где предпосылка верна.** Пометил 0.1% строк редким статусом:

```sql
UPDATE orders SET status = 'REFUNDED' WHERE id % 1000 = 0;   -- 1000 строк
CREATE INDEX idx_orders_refunded ON orders(created_at) WHERE status = 'REFUNDED';
```

| Индекс                            | Размер    | Отношение            |
| --------------------------------- | --------- | -------------------- |
| `idx_orders_status` (полный)      | 6856 kB   | —                    |
| `idx_orders_refunded` (частичный) | **40 kB** | в **170 раз** меньше |

Пока существует общий индекс по `status`, планировщик предпочитает его — он и так находит 1000 строк. Но если убрать общий, частичный подхватывает запрос без потери качества:

```
 ->  Bitmap Index Scan on idx_orders_refunded  (actual time=0.028..0.028 rows=1000 loops=1)
 Execution Time: 0.440 ms
```

Сорок килобайт делают работу семи мегабайт.

**1. В чём преимущество partial index?**
Он индексирует не всю таблицу, а только строки, попадающие под условие. Отсюда меньший размер, более быстрый поиск (дерево ниже) и — что часто важнее — дешевле запись: строки, не попадающие под условие, при вставке индекс вообще не трогают.

**2. В каких случаях он полезен?**
Когда запросы регулярно ходят за небольшим подмножеством: активные заказы среди архива, необработанные задачи в очереди, неудалённые записи (`WHERE deleted_at IS NULL`), ошибки в логах. Классика — статус, по которому работает приложение, при том что 99% строк давно в терминальном состоянии.

**3. Почему нельзя использовать один partial index для всех типов запросов?**
Потому что PostgreSQL применит его, только если сможет доказать, что условие запроса **гарантированно уже** условия индекса. Индекс `WHERE status = 'NEW'` не годится для запроса `WHERE status = 'PAID'` и даже для запроса вообще без условия на `status` — строк-то в нём не все. Каждое подмножество требует своего индекса.

## Часть 16. Expression Index

### Задание 18. Индекс по выражению

Таблица `users` в проекте уже существует и содержит рабочие данные, поэтому создана отдельная `lab_users` — 200 001 строка.

```sql
CREATE INDEX idx_lab_users_email ON lab_users(email);
EXPLAIN ANALYZE SELECT * FROM lab_users WHERE LOWER(email) = 'test@example.com';
```

```
 Gather  (cost=1000.00..4335.71 rows=1000) (actual time=25.050..26.831 rows=1 loops=1)
   ->  Parallel Seq Scan on lab_users  (actual rows=0 loops=2)
         Filter: (lower((email)::text) = 'test@example.com'::text)
         Rows Removed by Filter: 100000
 Execution Time: 26.877 ms
```

**Почему обычный индекс по `email` не используется?**
Потому что в индексе лежат **исходные** значения — `Test@Example.com`, `User1@Example.com`. А запрос ищет результат функции `LOWER(email)`. Для PostgreSQL `email` и `lower(email)` — разные выражения, и он не имеет права предполагать, что порядок сортировки исходных значений совпадает с порядком преобразованных. Индекс отбрасывается, остаётся полный проход.

Это общее правило: **любая функция или арифметика вокруг колонки делает обычный индекс по ней неприменимым.** `WHERE LOWER(email) = ...`, `WHERE date(created_at) = ...`, `WHERE price * 1.2 > 1000` — во всех случаях индекс по `email`, `created_at`, `price` работать не будет.

```sql
CREATE INDEX idx_lab_users_lower_email ON lab_users(LOWER(email));
```

```
 Index Scan using idx_lab_users_lower_email on lab_users  (cost=0.42..8.44 rows=1)
 Execution Time: 0.050 ms
```

| Метрика        | До                  | После        |
| -------------- | ------------------- | ------------ |
| Тип Scan       | `Parallel Seq Scan` | `Index Scan` |
| Execution Time | 26.877 ms           | **0.050 ms** |

**Ускорение в 537 раз.**

**Вывод: почему выражение в запросе влияет на возможность использования индекса?**
Индекс — это отсортированный список **конкретных значений**. Искать в нём можно только то, что в нём лежит. Обычный индекс хранит `email`, индекс по выражению — заранее вычисленный `LOWER(email)`. PostgreSQL сопоставляет выражение из `WHERE` с определением индекса буквально: совпало — использует, не совпало — игнорирует.

Практический вывод: либо приводить данные к нужному виду при записи, либо строить индекс ровно по тому выражению, которое стоит в запросе.

## Часть 17. Цена индексов

### Задание 19. Влияние индексов на INSERT

Две одинаковые таблицы, в одну добавлены пять индексов. В каждую вставлено по 200 000 строк одним запросом.

```sql
CREATE TABLE lab_ins_plain   (id BIGSERIAL PRIMARY KEY, user_id BIGINT, status VARCHAR(20),
                              amount NUMERIC(10,2), created_at TIMESTAMP);
CREATE TABLE lab_ins_indexed (... то же самое ...);

CREATE INDEX ON lab_ins_indexed(user_id);
CREATE INDEX ON lab_ins_indexed(status);
CREATE INDEX ON lab_ins_indexed(created_at);
CREATE INDEX ON lab_ins_indexed(amount);
CREATE INDEX ON lab_ins_indexed(user_id, status);
```

| Таблица           | Индексов      | Время вставки 200 000 строк |
| ----------------- | ------------- | --------------------------- |
| `lab_ins_plain`   | 1 (только PK) | **415 ms**                  |
| `lab_ins_indexed` | 6 (PK + 5)    | **1688 ms**                 |

**Замедление в 4.1 раза.** Каждый добавленный индекс обошёлся примерно в 250 мс на 200 тысяч строк.

**1. Как изменилось время выполнения INSERT?**
Выросло вчетверо.

**2. Почему?**
Вставка строки — это не только запись в таблицу. Для **каждого** индекса нужно: вычислить ключ, найти в дереве нужную страницу листа, вставить туда запись, при переполнении страницы разделить её надвое и обновить вышестоящие узлы. Плюс всё это пишется в WAL — журнал предзаписи, — то есть объём журнала тоже растёт пропорционально числу индексов.

**3. Что происходит с индексами при добавлении новой строки?**
Все индексы таблицы обновляются синхронно, в той же транзакции. Отложить нельзя: иначе следующий запрос увидел бы неполный индекс и вернул неверный результат.

Отдельно стоит помнить про `UPDATE`. В PostgreSQL обновление строки физически создаёт её новую версию, поэтому во все индексы добавляются новые записи, а старые остаются мусором до `VACUUM`. Оптимизация `HOT update` позволяет этого избежать, но только если изменённые колонки **не входят ни в один индекс** и в странице есть свободное место. Чем больше индексов — тем реже она срабатывает.

| --------------------- | ---------- |

| Все индексы (11 штук) | **238 MB** |

Индексы весят в **2.8 раза больше самих данных**.

**1. Какие индексы использовались чаще всего?**
`idx_orders_user_status` и `idx_orders_user_id` — они закрывают самые частые запросы по `user_id`.

**2. Есть ли неиспользованные?**
Да: `idx_orders_new` — частичный индекс по `WHERE status = 'NEW'`, который планировщик отверг как невыгодный. Ноль обращений, 5.5 МБ занято, замедление всех вставок. Кандидат на удаление в чистом виде.

У `idx_orders_status` тоже ноль, но по другой причине: он был пересоздан по ходу работы, а `CREATE INDEX` обнуляет счётчик.

**3. Можно ли автоматически считать индекс с `idx_scan = 0` бесполезным?**
Нет. Как минимум четыре причины:

- **Статистика с момента последнего сброса.** `pg_stat_reset()`, пересоздание индекса или перезапуск сервера обнуляют счётчики — ровно случай `idx_orders_status` выше.
- **Редкие, но важные запросы.** Месячный отчёт или ночная выгрузка обращаются к индексу раз в месяц; счётчик почти нулевой, а без индекса отчёт не отработает.
- **Уникальность.** Индекс за `UNIQUE` или `PRIMARY KEY` может не использоваться для чтения вообще, но он обеспечивает ограничение целостности. Удалять нельзя.
- **Реплики.** Счётчики локальны для узла. На основном сервере ноль, а на реплике, куда ходит аналитика, — миллионы обращений.

**4. Какие риски при удалении индекса?**
Основной — деградация под нагрузкой, которая проявится не сразу: план переключится на `Seq Scan`, и запрос, работавший 0.3 мс, начнёт занимать 300 мс. На тестовой базе, где всё в памяти, разницы можно и не заметить.

Вторая проблема — стоимость отката. Пересоздание индекса на большой таблице занимает минуты и блокирует запись, если делать без `CONCURRENTLY`.

Разумный порядок действий: убедиться, что статистика собиралась достаточно долго (недели, а не часы), проверить все реплики, а затем сначала выключить индекс из планирования (`UPDATE pg_index SET indisvalid = false`) и понаблюдать, и только потом удалять.

## Часть 19. Финальное задание на тестовой базе

### Задание 21. Оптимизация запроса

```sql
SELECT id, amount, status, created_at
FROM orders
WHERE user_id = $1
  AND status = 'PAID'
  AND created_at >= NOW() - INTERVAL '30 days'
ORDER BY created_at DESC
LIMIT 50;
```

**1–2. План до оптимизации** (с индексами, накопленными к этому моменту):

```
 Limit  (cost=0.43..8.45 rows=1 width=29) (actual time=0.233..0.233 rows=0 loops=1)
   ->  Index Scan using idx_orders_user_created_at_desc on orders
         Rows Removed by Filter: 3
 Execution Time: 0.267 ms
```

**3. Проблемы.**
Индекс `(user_id, created_at DESC)` закрывает два условия из трёх, а `status` остаётся в `Filter` — строки поднимаются из таблицы и отбрасываются уже после чтения. На этом пользователе отброшено всего три, но на активном пользователе с тысячами заказов отбрасываться будет пропорционально больше.

**4–5. Предлагаемый индекс и порядок колонок.**

```sql
CREATE INDEX idx_orders_user_status_created ON orders(user_id, status, created_at DESC);
```

Обоснование порядка — правило «равенства вперёд, диапазон последним»:

| Позиция | Колонка           | Условие               | Почему здесь                                                               |
| ------- | ----------------- | --------------------- | -------------------------------------------------------------------------- |
| 1       | `user_id`         | равенство             | самое селективное, сразу отсекает почти всё                                |
| 2       | `status`          | равенство             | сужает оставшееся; после диапазона был бы бесполезен                       |
| 3       | `created_at DESC` | диапазон + сортировка | диапазон обязан быть последним; `DESC` даёт готовый порядок для `ORDER BY` |

Поставить `created_at` вторым нельзя: после колонки с диапазоном индекс дальше не сужается, и `status` пришлось бы снова проверять фильтром.

**6–8. Результат.**

```
 Limit  (cost=0.43..8.45 rows=1 width=29) (actual time=0.052..0.067 rows=4 loops=1)
   ->  Index Scan using idx_orders_user_status_created on orders
 Execution Time: 0.099 ms
```

| Метрика                | До                                | После                            |
| ---------------------- | --------------------------------- | -------------------------------- |
| Тип Scan               | `Index Scan` + `Filter`           | `Index Scan`                     |
| Execution Time         | 0.267 ms                          | **0.099 ms**                     |
| Rows Removed by Filter | 3                                 | **0**                            |
| Sort                   | —                                 | —                                |
| Используемый индекс    | `idx_orders_user_created_at_desc` | `idx_orders_user_status_created` |

Для контроля тот же запрос выполнен с запретом на использование нового индекса: план вернулся к `Bitmap Heap Scan` + `Sort` (0.134 мс). Новый индекс закрывает все три условия и сортировку одновременно: ни `Filter`, ни `Sort` в плане не осталось.

Абсолютные значения здесь малы — выборка возвращает 4 строки и целиком лежит в памяти. Значение имеет форма плана: она не изменится при росте таблицы, тогда как `Filter` и `Sort` дорожали бы пропорционально числу заказов пользователя.

| Можно ли улучшить существующий         | нечего улучшать — индекс только по `id` |                   |                    |
| Можно ли изменить сам SQL              | нет, запросы минимальны                 | нет               | нет                |

Селективность всех трёх запросов исключительно высокая — возвращается менее сотой доли процента таблицы. Это тот диапазон, где индекс даёт наибольший выигрыш.

Дополнительная проблема Query 2 и Query 3 — узел `Sort`. Сортировка по `created_at` не может быть удовлетворена существующими индексами, а `LIMIT` без упорядоченного доступа не позволяет прекратить чтение досрочно.

Переписывание SQL ничего не даст: запросы уже содержат минимально необходимый набор условий, лишних соединений и подзапросов в них нет. Проблема не в формулировке запросов, а в отсутствии структуры доступа.

# Часть 21. Оптимизация собственного сервиса

## Задание 27. Выбор запроса и обоснование индекса

Для оптимизации выбран **Query 3** — основная выборка истории сессий. Обоснование выбора: это самый частый запрос сервиса, он же худший по времени (34.760 ms), и он же содержит все проблемные элементы сразу — отбор по `user_id`, сортировку по `created_at` и `LIMIT`.

Предлагаемый индекс:

```sql
CREATE INDEX idx_play_sessions_user_created
    ON play_sessions (user_id, created_at DESC);
```

Обоснование порядка колонок:

| Позиция | Колонка           | Роль в запросе        | Почему здесь                                                                                                                               |
| ------- | ----------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 1       | `user_id`         | равенство             | равенство ставится первым: оно фиксирует одно значение, и внутри него следующая колонка остаётся упорядоченной                             |
| 2       | `created_at DESC` | диапазон + `ORDER BY` | диапазон обязан быть последним, дальше индекс не сужается; `DESC` совпадает с направлением сортировки в запросе и избавляет от узла `Sort` |

Обратный порядок `(created_at, user_id)` не подошёл бы: сессии одного пользователя оказались бы разбросаны по всему индексу, и отбор по `user_id` потребовал бы полного его просмотра.

Вторым индексом добавлен `(created_at)` для агрегирующего запроса статистики — там отбор идёт только по времени, поэтому индекс одноколоночный.

## Задание 28. Реализация через миграцию

Индексы добавлены changeset'ом Liquibase — `db/changelogs/008_play_sessions_indexes.sql`, подключённым в `db/changelog.xml`. Изменение воспроизводится при запуске проекта на любой машине и не существует только в локальной базе.

```sql
--liquibase formatted sql

--changeset kirill:8
CREATE INDEX IF NOT EXISTS idx_play_sessions_user_created
    ON play_sessions (user_id, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_play_sessions_created_at
    ON play_sessions (created_at);

--rollback DROP INDEX idx_play_sessions_user_created;
--rollback DROP INDEX idx_play_sessions_created_at;
```

# Часть 23. Финальный вопрос

## Задание 30. Почему нельзя индексировать всё?

**Размер индексов и стоимость хранения.**
Индекс хранит копию значений колонки плюс адрес строки, поэтому его размер сопоставим с объёмом данных. Измерения по ходу работы:

| Таблица                     | Данные | Индексы | Отношение |
| --------------------------- | ------ | ------- | --------- |
| `play_sessions` (2 индекса) | 63 MB  | 73 MB   | 1.16      |
| `orders` (11 индексов)      | 85 MB  | 238 MB  | **2.8**   |

На таблице `orders` индексы заняли почти втрое больше места, чем сами данные. Отдельно дорого обходятся покрывающие индексы: `idx_orders_user_id_include` с четырьмя колонками в `INCLUDE` занял 52 МБ — больше половины таблицы в одиночку.

Последствия выходят за рамки места на диске: индексы конкурируют с данными за оперативную память. Раздутый набор индексов вытесняет из буферного кэша сами таблицы, и запросы начинают читать с диска то, что раньше находили в памяти.

**INSERT.**
Прямое измерение на двух одинаковых таблицах по 200 000 строк:

| Индексов      | Время вставки |
| ------------- | ------------- |
| 1 (только PK) | 415 ms        |
| 6 (PK + 5)    | **1688 ms**   |

Замедление в 4.1 раза, около 250 мс на каждый индекс. Причина в том, что вставка строки — это не только запись в таблицу: для каждого индекса нужно вычислить ключ, найти страницу листа, вставить запись, при переполнении разделить страницу и обновить вышестоящие узлы. Всё это дополнительно пишется в WAL, поэтому объём журнала также растёт пропорционально числу индексов.

**UPDATE.**
В PostgreSQL обновление строки физически создаёт её новую версию. Записи добавляются во все индексы таблицы, а старые остаются мусором до `VACUUM`. Оптимизация `HOT update` позволяет обойтись без обновления индексов, но срабатывает только если изменённые колонки не входят ни в один индекс и в странице есть свободное место. Чем больше индексов покрывают колонки таблицы, тем реже выполняется это условие.

**DELETE.**
Удаление строки не убирает записи из индексов немедленно — они помечаются и удаляются позже, при `VACUUM`. До этого момента индексы продолжают занимать место и просматриваться при поиске. Чем больше индексов, тем больше работы у `VACUUM` и тем дольше он держит нагрузку на систему.

**Влияние на скорость записи в целом.**
Все перечисленные операции выполняются синхронно, в той же транзакции: отложить обновление индекса нельзя, иначе следующий запрос увидел бы неполный индекс. Поэтому стоимость индексов платится при каждой записи, а выигрыш получается только при чтении. Для таблицы вроде `play_sessions`, куда идёт непрерывный поток вставок, это соотношение особенно важно.

**Реальное использование запросами.**
Индекс приносит пользу, только если его выбирает планировщик. По ходу работы получены два наглядных контрпримера:

- `idx_orders_new` — частичный индекс по `WHERE status = 'NEW'`: `idx_scan = 0`, 5.5 МБ занято, все вставки замедлены, пользы ноль. Планировщик отверг его, поскольку `NEW` покрывает 25% таблицы и индексный доступ оказался дороже полного сканирования.
- `play_sessions_pkey` — индекс по `id`: `idx_scan = 0`, 21 МБ. Ни один запрос сервиса не ищет сессии по идентификатору. Удалить его при этом нельзя — он обеспечивает `PRIMARY KEY`.

Обратный случай: индекс по колонке низкой кардинальности заведомо не будет использован. При четырёх значениях `status` каждое покрывает четверть таблицы, и планировщик предпочтёт `Seq Scan`.

**Вывод.**
Индексы — не бесплатное улучшение, а сделка: ускорение чтения покупается за место на диске, память и скорость записи. Индексировать имеет смысл не колонки, а **конкретные запросы**, которые действительно выполняются, и только после того, как `EXPLAIN ANALYZE` подтвердил наличие проблемы. Проверять фактическое использование следует по `pg_stat_user_indexes`, а не по предположениям о том, какие запросы «наверное, будут».
